# worker/

Standalone background-job process for eStudyou. Not part of the Next.js app — it's a plain Node/TypeScript process (`tsx`) that boots, starts three independent polling loops, and exposes a minimal HTTP health endpoint. Deployed as its own DigitalOcean App Platform `worker` component (see `.do/app.yaml`), built from its own `worker/Dockerfile`, separate from the `web` service.

## Files

- **`package.json`** — name `the-learning-nexus-worker`. Scripts: `dev` (`tsx watch src/index.ts`), `start` (`tsx src/index.ts`), `typecheck`. Only real dependency is `dotenv`; deliberately has **no** `@prisma/client`/`prisma` dependency of its own (see "Shared Prisma client" below).
- **`tsconfig.json`** — `baseUrl: ".."` with `"@/*": ["./*"]`, i.e. the `@/` alias inside worker code points at the **repo root**, the same alias the main Next.js app uses. This is what lets worker source files `import prisma from "@/prisma"` and `import { createNotification } from "@/app/lib/notifications"` — worker imports shared business logic straight out of `app/lib/**` rather than duplicating it.
- **`Dockerfile`** — must be built with the **repo root** as build context, not `worker/` (see `.do/app.yaml`: `source_dir: /`, `dockerfile_path: worker/Dockerfile`). It does a full root `pnpm install --frozen-lockfile` + `pnpm prisma generate` first (this is what actually produces `@prisma/client` at runtime), then `COPY`s the whole `app/` tree (needed because worker imports out of `app/lib/**`), then separately installs worker's own much smaller dependency set from `worker/package.json`/`worker/pnpm-lock.yaml`.
- **`pnpm-lock.yaml`** — worker's own lockfile, scoped to its own tiny dependency set (`dotenv`, `tsx`, `typescript`). Note `pnpm-workspace.yaml` at the repo root only lists `"."` as a workspace package — `worker/` is **not** a pnpm workspace member, it's installed independently.

## `src/`

- **`index.ts`** — the entry point. Starts three `setInterval` polling loops (each also runs once immediately on boot):
  - `runCompletionCheck` → `markCompletedClasses()`, every 5 minutes.
  - `runRegularClassMaterialization` → `materializeAllActiveSeries()`, every 6 hours.
  - `runRefundExpirySweep` → `sweepExpiredRefundRequests()`, every 1 hour.
  Each loop's `try/catch` isolates failures — one loop erroring doesn't kill the process or block the others. Each also tracks `lastXCheckAt` timestamps, exposed via a bare `http.createServer` on `PORT` (default 8081) at `GET /health`: returns `503` if any loop hasn't completed a run within 2× its own interval (i.e. detects a *stalled* loop, not just "process still running" — the same reasoning as `app/api/health/route.ts`'s DB check, just applied to the worker's own loops instead of DB connectivity).
- **`complete-classes.ts`** — `markCompletedClasses()`. Finds all `Class` rows with `status: "scheduled"` whose `startTime + durationInHours` has passed, and for each one: does a compare-and-swap `updateMany({ where: { id, status: "scheduled" }, data: { status: "completed", ... } })` so this poller and the manual "Mark Complete" UI action can't double-process the same class (a `count === 0` result means someone else already completed it, so it's skipped). On a successful claim: triggers the teacher payout (`transferPayoutForClass`, no-ops gracefully if the teacher hasn't onboarded to Stripe Connect), awards gems/sparks, rolls a "lucky bonus," checks session-count badges, updates activity streaks, and notifies both parties. Each class is processed in its own `try/catch` so one broken class can't block completion for every other class in the same run. **This is currently the only place in the codebase that ever sets `Class.status = "completed"`.**
- **`expire-refund-requests.ts`** — `sweepExpiredRefundRequests()`. Finds `RefundRequest` rows still `pending` past their `expiresAt`, calls `expireIfNeeded` (`app/lib/refund-requests/expire-refund-request.ts`) on each. Exists because `expireIfNeeded` was previously only ever invoked opportunistically — when a student/teacher/admin happened to view that specific request — so a request nobody looked at again could stay `pending` forever. This sweep makes expiry unconditional on a schedule instead.
- **`regular-classes.ts`** — `materializeAllActiveSeries()`. For every `RegularClass` with `status: "active"`, calls `materializeOccurrences` (`app/lib/regular-classes/materialize-occurrences.ts`) to generate the next rolling window of concrete `Class` occurrences from the recurring series definition.
- **`complete-classes.test.ts`**, **`expire-refund-requests.test.ts`** — Vitest coverage for the two corresponding jobs (test authoring/maintenance is `vitest-qa-engineer`'s domain; not re-described here).

## Why a separate process, and why it must never scale past 1 instance

`.do/app.yaml` explicitly comments: *"one single-instance `worker` (it's a polling loop with no distributed lock — never raise `instance_count` above 1)"*, and the spec sets `instance_count: 1` for the `worker` component. None of the three jobs above take a lock before acting — `markCompletedClasses`'s compare-and-swap protects against racing with the *manual* completion action, but two worker instances polling simultaneously would both read the same "due" rows and race each other on the same `updateMany`/`findMany` + mutate pattern, risking duplicate payouts, duplicate gem/spark awards, or duplicate notifications. If this ever needs to scale, it needs a real distributed lock (or to be moved to a proper job queue) first — don't just bump `instance_count`.

It's a separate DO App Platform component (rather than, say, a cron hitting an API route on `web`) so it can run continuously with in-process `setInterval` timers independent of the web service's request/response lifecycle and autoscaling.

## The shared-Prisma-client landmine

Worker has no `@prisma/client` or `prisma` dependency in its own `package.json` — on purpose. At runtime, `import prisma from "@/prisma"` inside worker code resolves (via the `tsconfig.json` path mapping above) to the repo root's `prisma/index.ts`, which does `new PrismaClient()` from `@prisma/client`. That `@prisma/client` package itself is resolved via plain Node module resolution walking *up* from `worker/node_modules` to the repo root's `node_modules/@prisma/client` — the one generated by running `pnpm prisma generate` at the repo root. Worker never generates or installs its own copy; it structurally depends on the root's already-generated client being present.

**This is why running `pnpm install` or `prisma generate` from inside `worker/` is dangerous**: doing so gives `worker/` its own separate, independent install/generation step that competes with — and can desync from — the root project's generated client and node_modules layout that both the `web` service and this worker are assuming is the single source of truth. Always run `pnpm install` and `pnpm prisma generate` from the **repo root**, never from inside `worker/`.
