During a repo-wide documentation task (writing README.md files across app/lib/classes, app/lib/availability, app/lib/regular-classes, app/lib/refund-requests, app/lib/actions, and the corresponding app/ui/main/** and app/main/** UI directories), re-reading `classes.actions.ts` and related files end-to-end surfaced that this agent's own system-prompt "Known gaps" section is out of date as of 2026-08-05:

1. **Completion mechanism exists now.** `completeClass` in `classes.actions.ts` (manual, compare-and-swap against `status: "scheduled"`) plus `worker/src/complete-classes.ts`'s `markCompletedClasses` (periodic poller, same compare-and-swap idiom) both set `status: "completed"`. The old "nothing ever sets completed" framing is gone. A full no-show/refund-dispute domain (`RefundRequest`, `app/lib/actions/refund-requests.actions.ts`, `app/lib/refund-requests/expire-refund-request.ts`) is now built on top of this and is fully wired (student report → teacher accept/refuse → student escalate → admin resolve, with a 5-day auto-expire-to-refund path).
2. **`priority` flag is no longer inert.** `fetchOpenRequestsForTeacher` now orders `[{ priority: "desc" }, { startTime: "asc" }]`, and `app/ui/main/classes/open-requests.tsx` renders a "Priority" badge on flagged rows. Confirmed both server and UI sides are live.
3. **`cancelClassCore` soft-cancels, not hard-deletes.** Sets `status: "cancelled"` via `prisma.class.update`, specifically because `Payment.class` cascades on delete and a hard delete would destroy the refund's own paper trail. This applies to *all* cancellations now, not just regular-class occurrences (though the RegularClass materialization watermark logic that depends on soft-cancel still applies exactly as documented in `app/lib/regular-classes/materialize-occurrences.ts`).
4. **Notifications now poll.** `app/ui/main/notifications/notification-dropdown.tsx` polls `fetchNotificationsForUser` every 20s (skipped while `document.visibilityState !== "visible"`). The "no polling/websocket/SSE, seed-once only" framing is gone. `TYPE_CONFIG`'s icon map is still incomplete though — covers class_* and refund_* types but not gamification, counter-offer, regular_class_*, or payout_* NotificationType values.

**Why this matters**: the role's static background material (system prompt) is a snapshot from whenever it was last written and this codebase moves fast — always re-verify "known gaps" claims against the actual files (`classes.actions.ts`, `worker/src/*.ts`) before repeating them to a user, rather than treating the system-prompt framing as current truth. This is a concrete instance of the "treat classes.actions.ts as canonical over any summary, including the one in your own instructions" rule already stated in the role, worth remembering as a recurring failure mode to watch for.

**Also found**: `app/main/admin/refund-requests/page.tsx`'s "other requests" table links to `/main/teacher/refund-requests/${id}` (the teacher-only detail route, gated by `req.teacherId !== user.id`) instead of an admin-scoped route — likely a copy-paste bug, not intentional. No `app/main/admin/refund-requests/[id]/page.tsx` exists. Flagged to the user, not fixed (doc-only task).
