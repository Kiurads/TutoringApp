# app/lib/actions

A single flat directory of Next.js Server Actions (`"use server"`) spanning almost every domain in the app — class booking/lifecycle, availability, notifications, refund/no-show disputes, recurring classes, Stripe payments/payouts, the gamification store and review pipeline, and general user/teacher/student/subject CRUD. One subdirectory, `teachers/`, holds two more teacher-specific actions kept out of the already-large `teachers.actions.ts`.

Files here are the "framework-attached" half of their domain: they carry `"use server"`, call `auth()` to identify the caller, and are imported directly by pages/forms/UI components. Several domains keep a parallel *framework-free* implementation elsewhere (`app/lib/<domain>/...` or a top-level `app/lib/*.ts`) that both this layer and the background `worker/` process call into — e.g. `expire-refund-request.ts`, `materialize-occurrences.ts`, `payouts.ts`. That split exists specifically so the worker doesn't have to import the whole NextAuth/Prisma-adapter chain just to run a scheduled sweep. Look for that pattern throughout this README — it's the single most important structural idea in this directory.

## Class lifecycle & booking — `classes.actions.ts`

The largest, most important file in the codebase (~1090 lines). Owns everything that happens to a `Class` row after creation (creation itself lives in `app/lib/classes/`, see that directory's README).

**Fetchers** — each shapes data differently; don't assume they're interchangeable:
- `fetchClasses` / `fetchClassById` — full `ClassData` shape (teacher/student/subject joined, `hasPreAuth` derived from `!!preAuthIntentId`, `counterOfferTime` as ISO string or null).
- `fetchClassesByUser` — lighter `ClassDataSimple` shape, no joins, ordered `startTime desc`.
- `fetchUpcomingClassesByUser` — filters `startTime > now`, full joins, used for "what's coming up" views.
- `fetchBookedClassesByUser` — computes a `requestedBySelf` boolean (`requester.id === viewer.id`) that the student/teacher table-button components (`app/ui/main/classes/student-table-buttons.tsx`, `teacher-table-buttons.tsx`) depend on to decide whether to render Accept/Refuse or Cancel — a class the viewer themself requested should never show an Accept/Refuse action back to them.
- `fetchClassRequestedBySelf`, `fetchClassSubjectsBySelf` — small per-class/self-scoped helpers.
- `fetchClassBySelfCalendar` — feeds the calendar UI. Its `ClassDataCalendar.startTime` is documented inline as deliberately a full ISO 8601 UTC string, *not* pre-split into a server-local date/time pair — a student and teacher in different timezones each need the browser to convert it to their own local time, which only the client can do. Format it client-side via `new Date(startTime)`, never assume server-local time.

**`cancelClassCore(classId, user)`** — the authorization + refund-tier + notify logic, with no `redirect()`, returning an error string or `null`. This is the function to read if you need to understand cancellation:
- Authorization: caller must be the class's own student, its own teacher, or an admin.
- A `completed` class can never be cancelled — its teacher payout may already be transferred, so cancelling afterward would let the platform refund the student while the teacher keeps the payout.
- Unpaid + has a `preAuthIntentId` → just cancels the Stripe hold (best-effort; a `catch` swallows an already-expired hold).
- Paid → time-based refund tiers: **>24h before start → full Stripe refund + `reverseClassPoints`**; **12–24h → 50% refund (rounded cents) + `reverseClassPoints`** (the *full* points award is clawed back even on a half refund — the inline comment explains gems/sparks aren't meaningfully divisible, and the award was for the class happening, not which fraction got refunded); **≤12h → no refund, no point reversal**. A failed Stripe refund call aborts the whole cancellation (`return` an error) rather than cancelling with no refund.
- **Soft-cancels, not hard-deletes**: sets `status: "cancelled"` via `prisma.class.update`. The inline comment is explicit about why: `Payment.class` cascades on delete, so hard-deleting the `Class` row would also wipe out the `Payment` row that documents the refund that was just issued — the cancellation would leave no paper trail. *(This is a meaningful correction versus older documentation of this codebase, which described cancellation as a hard delete — re-verify against the actual file before trusting any summary, including this one, on this point.)*
- Notifies the counterparty (`class_cancelled`), with the message text branching on whether the teacher or the student initiated the cancellation.

**`cancelClassById(classId)`** — the redirecting wrapper used directly by UI actions: resolves the session, calls `cancelClassCore`, then `revalidatePath` + `redirect` to the caller's own classes list with a `?toast=cancelled` param.

**Why `cancelClassCore` exists separately**: `regular-classes.actions.ts`'s `cancelRegularClass` needs to cancel *every future occurrence* of a series in a loop. `redirect()` in Next.js works by throwing a special control-flow error — calling the redirecting `cancelClassById` inside a loop would abort the entire loop (and the series-level notification after it) on the very first occurrence. `cancelClassCore` has no `redirect`, so the loop can `try/catch` around each occurrence (isolating one failure from the rest — see that file's own comment) and only redirect once, after the whole batch finishes.

**`acceptClassById(classId)`**:
- Authorization: must be a participant (student/teacher/admin) **and must not be the class's own `requesterId`** — you can't accept your own request.
- Rejects if the teacher now has a conflicting `scheduled` class (`teacherHasSchedulingConflict`, excluding this class id) — covers the case where two students requested overlapping times and the teacher already accepted one.
- **Compare-and-swap via `updateMany({ where: { id, status: "requested" }, data: { status: "scheduled" } })`, checking `claim.count === 0` to bail out.** This claims the transition before any side effect runs, specifically to guard against a double-click or retried accept re-running the Stripe capture, gem/spark awards, and notifications a second time. This is the same defensive pattern used in `claimClass` (below) and in the worker's `markCompletedClasses`/this file's `completeClass` — **preserve it in any refactor of this function.**
- If a pre-auth intent exists, captures it here (`stripe.paymentIntents.capture`), creates the `Payment` row, marks `paid: true`, and awards +50 gems to the student. **This capture happens here, in the accept action — not in the Stripe webhook.** That's a deliberate cross-file design decision shared with the stripe-payments-engineer domain: acceptance is the actual "the deal is on" moment, so capture is tied to it directly rather than to an async webhook event.
- Awards +50 sparks to the teacher unconditionally (separate from the pre-auth gem award above).
- Notifies whichever side didn't initiate the request.

**`refuseClassById(classId)`** — same authorization shape as accept, releases any pre-auth hold (`paymentIntents.cancel`, best-effort), sets `status: "refused"`, notifies.

**`fetchOpenRequestsForTeacher(teacherEmail)`** — matches `teacherId: null, status: "requested"` rows against the teacher's subjects. **Orders by `[{ priority: "desc" }, { startTime: "asc" }]`.** The inline comment explains: `priority` is set on a broadcast `Class` row when the requesting student has a `StudentGameProfile.priorityBooking` perk active (a one-shot gem-store purchase, consumed at request time in `create-class-as-student.ts`), and this ordering is "the only place it can matter" — it purely controls which teacher sees an open request first, ties still broken by `startTime`. *(If you've read older documentation/background describing `priority` as stored-but-inert/dead, that has since been fixed — re-check this file directly, as instructed, rather than trusting a prior summary.)*

**`claimClass(classId)`** — a teacher claims an open broadcast request. Computes `totalPrice` from the claiming teacher's own `pricePerHour` (broadcast requests are created with `totalPrice: 0` since no teacher was assigned yet). Checks `teacherHasSchedulingConflict` first, then does the actual claim via **`updateMany({ where: { id, teacherId: null, status: "requested" }, data: { teacherId, status: "scheduled", totalPrice } })`** — a compare-and-swap re-checking `teacherId: null, status: "requested"` at write time, not just at the earlier read, closing the race window between two teachers claiming the same request simultaneously. On `claim.count === 0` (someone else won the race), it silently no-ops rather than throwing. **This is the one piece of real concurrency-safety modeled explicitly in this file's own comment as "same pattern as `payouts.ts`" — preserve this re-check in any refactor.**

**`completeClass(classId)`** — a *manual* "mark complete" action (student or teacher can trigger it once the class's end time has passed; the UI is `app/ui/main/classes/details/complete-class-button.tsx`). Uses the same compare-and-swap pattern (`updateMany` on `status: "scheduled" → "completed"`) to guard against racing the worker's own periodic completion sweep (`worker/src/complete-classes.ts`'s `markCompletedClasses`) — whichever caller actually flips the status proceeds with payment capture, payout, and gamification; the other sees `claim.count === 0` and returns `{}` (silently, not an error, since the class did get completed — just by the other caller). Falls back to capturing an uncaptured pre-auth if one exists (`preAuthIntentId && !paid`), calls `transferPayoutForClass`, awards gems/sparks/badges/streaks to both sides, and notifies the student to leave a review.
- **This directly closes what used to be documented as "the platform's biggest known gap — nothing ever sets `completed`."** That gap is closed now via two paths: this manual action, and the worker's periodic poller (`worker/src/complete-classes.ts`, same compare-and-swap idiom, run on an interval alongside the regular-classes materialization job). If you're relying on older documentation that says nothing sets `completed`, it's stale — verify directly against this file and `worker/src/complete-classes.ts`.

**Counter-offers** — `proposeCounterOffer` (only while `status === "requested"`, sets `counterOfferTime`, notifies the student), `acceptCounterOffer` (moves `counterOfferTime` into `startTime` and clears the field, redirects with `?toast=time_accepted`), `declineCounterOffer` (just clears the field, redirects with `?toast=time_declined`). Both accept/decline require the caller to be the class's `requesterId` (or admin) — the *other* party proposed the counter-offer, so only the original requester can accept/decline it. All the surrounding UI lives in the shared, role-parameterized `app/ui/main/classes/details/class-action-modals.tsx`.

**Gotchas specific to this file**:
- `teacherId` is nullable on `Class` (broadcast requests before claiming) — every query/UI touching `class.teacher` must null-check; this file consistently does (`cls.teacher ? ... : null` / `"TBD"` / `"Your teacher"` fallback strings throughout).
- Authorization checks are present on most mutating actions here but the pattern is copy-pasted per function rather than centralized — when adding a new mutating action, follow the existing `isParticipant` shape rather than assuming a shared guard exists.
- `classes.actions.test.ts` (34KB) is the main regression net, covering the no-session paths, the transactional claim/accept/complete races, and broadcast-mode edge cases — extend it alongside any change here.

## Availability — `availability.actions.ts`

- `fetchAvailability(teacherId)` — reads a teacher's `TeacherAvailability` rows, sorted by day/hour/minute.
- `setAvailability(slots)` — auth-gated to `role === "teacher"`. Does a **full delete-then-recreate inside one `prisma.$transaction`** (`deleteMany` then `createMany`) rather than diffing — simpler than reconciling adds/removes, and the transaction guarantees a teacher never has a half-updated schedule visible mid-write. Keep that atomicity if you touch it.
- The actual enforcement of these slots against booking attempts happens in `app/lib/availability/check-availability.ts`'s `isWithinAvailability` (see that directory's README) — this file only manages the slot data, it doesn't enforce anything itself.

## Notifications — `notifications.actions.ts`

- `fetchNotificationsForUser(email)` — the most recent 30 notifications for a user, newest first. This is a one-shot fetch, not a subscription — see `app/lib/notifications.ts` for the creation side and the "not live" caveat.
- `markNotificationRead` / `markAllNotificationsRead` — both call `revalidatePath("/main/student", "layout")` **and** `revalidatePath("/main/teacher", "layout")` unconditionally, regardless of the caller's actual role. Simpler than branching on role, at the cost of one wasted revalidation per call.
- Notifications are otherwise only ever *created* from other actions (`createNotification` in `app/lib/notifications.ts`, called from `classes.actions.ts`, `regular-classes.actions.ts`, `refund-requests.actions.ts`, `paymets.actions.ts`, `payouts.actions.ts`, and the gamification hooks) — this file has no "create" export of its own.

## Refund requests / no-show disputes — `refund-requests.actions.ts`

A full dispute-resolution state machine layered on top of `Class`: a student reports a teacher no-show on a `completed` + `paid` class → the teacher has a window to accept or refuse → a refused report can be escalated to admin → admin makes the final call. Status flow: `pending → accepted | refused → (refused →) admin_review → resolved`, or `pending → expired` if the teacher never responds within the window (handled by `expireIfNeeded`, see `app/lib/refund-requests/README.md`).

- **`createRefundRequest(classId, reason)`** — student-only. Validates the class is `completed`, `paid`, has an assigned teacher, and has no existing `RefundRequest` for it (one-to-one via a `classId` unique constraint). Sets `expiresAt` to `now + EXPIRY_DAYS` (5 days). Notifies the teacher (`refund_requested`).
- **`escalateToAdmin(requestId)`** — student-only, and only valid from `status === "refused"` — moves it to `admin_review` and notifies every admin user.
- **`acceptRefundRequest`/`refuseRefundRequest`** — teacher-only, only valid from `pending`. Accept triggers an immediate Stripe refund (if a `Payment` exists) and `reverseClassPoints`; a failed Stripe call surfaces as an error and does **not** flip the status (unlike `cancelClassCore`'s refund-tier logic, there's no partial/tiered refund here — a no-show refund is always full).
- **`adminResolveRefundRequest(requestId, action, adminNote?)`** — only valid from `admin_review`; `action: "refund"` issues the Stripe refund + point reversal, `"dismiss"` doesn't. Either way sets `status: "resolved"` and notifies both sides.
- **The dual-invocation expiry pattern**: `fetchRefundRequestByClassId`, `fetchRefundRequestsForTeacher`, and `fetchRefundRequestByIdForTeacher` all call `expireIfNeeded` (from `app/lib/refund-requests/expire-refund-request.ts`) **lazily**, on read, before returning data — so a student/teacher viewing an overdue request sees it as already-expired/refunded immediately, without waiting for the next worker sweep. The worker (`worker/src/expire-refund-requests.ts`) calls the *same* function on its own periodic schedule as a backstop for requests nobody happens to view. This is the same shared-core pattern described in that file's own README — re-read it if you're touching either side.

## Regular (recurring) classes — `regular-classes.actions.ts`

Server-action wrapper around the `RegularClass` template: `requested → active → inactive`. See `app/lib/regular-classes/README.md` for the occurrence-materialization mechanics (watermark, off-session charging) — this file is the auth-gated request/accept/refuse/cancel/fetch layer around that engine.

- **`requestRegularClass`** — student picks a specific teacher, day of week, time, duration; computes `totalPrice` via the same `computeClassPrice` used for one-off classes (no Study Boost consideration here — this is a template, not a single purchase); creates the `RegularClass` at `status: "requested"`; notifies the teacher.
- **`acceptRegularClass`** — teacher/admin only, only from `status: "requested"`. Flips to `active` **and immediately calls `materializeOccurrences`** so the student sees their first occurrence(s) right away rather than waiting for the next worker tick.
- **`refuseRegularClass`** — flips to `inactive`, no occurrences ever get created since `materializeOccurrences` no-ops for a non-`active` series.
- **`cancelRegularClass`** — any participant or admin. Flips the series to `inactive`, then queries future non-terminal occurrences (`startTime > now`, `status in [requested, scheduled]`) and calls `cancelClassCore` (not `cancelClassById` — see the explanation under `classes.actions.ts` above for why) on each inside a `try/catch` loop that isolates one occurrence's failure from the rest, so one bad row can't leave the whole batch (and the final notification) unprocessed. Past/completed/already-refused occurrences are left untouched — the query only ever targets future rows.
- Fetchers (`fetchRegularClassesByStudent/Teacher/ById`) share a `formatRegularClass` mapper that renders `startTime` as an `"HH:MM"` string (the template only stores a wall-clock time-of-day + `dayOfWeek`, not a specific date — actual dated occurrences are the materialized `Class` rows, not this record).

## Payments, payment methods, and payouts (Stripe domain — cross-owned with stripe-payments-engineer)

Two coexisting payment flows exist in this app, and these files sit on both sides of them:

- **`paymets.actions.ts`** *(the filename really is spelled this way — `paymets`, not `payments`; it's the actual, intentional filename, not a typo to "fix")*. Read-side (`fetchPaymentsByUserId`, `fetchPaymentsByTeacherId` — note `teacherPayoutAmount` here falls back to gross `amount` for any pre-migration row that predates the payout-split columns, so the UI never shows a blank payout; `fetchPaymentReceipt`, viewer-scoped so a student can't pull up a teacher's receipt or vice versa) plus **`createPaymentForClass(classId, paymentIntentId)`** — the entry point for the **immediate-capture** flow (as opposed to pre-auth). Creates the `Payment` row (with the platform-fee/payout split via `computeCommissionSplit`), marks the class `paid: true`, notifies the teacher (`class_paid`), and awards the student +50 gems. This is the same immediate-capture shape reused unchanged for recurring-class occurrences in `materializeOccurrences` (see that file) — **recurring occurrences deliberately never use pre-auth**, by design, not omission.
- **`payment-methods.actions.ts`** — `saveDefaultPaymentMethod(setupIntentId)` persists a student's saved card (from a Stripe SetupIntent) as their default for the recurring-class off-session charge flow. Re-fetches the SetupIntent from Stripe server-side and checks it belongs to the caller's own `stripeCustomerId` rather than trusting the client-supplied id — a deliberate anti-tampering check. `getPaymentMethodStatus` is a simple boolean existence check used to gate UI (e.g. "add a card before requesting a recurring class").
- **`payouts.actions.ts`** — `startConnectOnboarding` generates a fresh Stripe Express account-onboarding link (creating the Connect account first via `ensureConnectAccount` if needed); explicitly never cached/stored since Account Links are single-use and expire within minutes — must be regenerated on every click. `getConnectStatus` surfaces the teacher's Connect state to the UI. `retryFailedPayout` is admin-only and simply re-invokes `transferPayoutForClass` (from the top-level `app/lib/payouts.ts`) — that function's own compare-and-swap already accepts retrying a `"failed"` `payoutStatus`, so this isn't a separate retry mechanism, just an admin-facing trigger for the same path a normal class completion goes through.
- **The pre-auth capture point**: pre-authorized payments (created via `createClassWithPreAuth` in `app/lib/classes/`) are captured in **`acceptClassById`** and, as a fallback, in **`completeClass`** — both in `classes.actions.ts` — **not** in the Stripe webhook handler. This cross-file relationship (payments domain's capture logic actually living in the class-lifecycle file) is intentional and worth knowing before assuming the webhook is where money moves for pre-auth'd classes.
- **`stripe.ts`** (this directory, not `app/lib/stripe.ts`) — **dead code.** A leftover Stripe Checkout Sessions "embedded checkout" quickstart (`fetchClientSecret`), with a literal `"{{PRICE_ID}}"` placeholder never filled in. Confirmed via grep that `fetchClientSecret` is never imported anywhere in the app. Don't treat this as a wired-up alternative payment path — it isn't connected to anything. (Not to be confused with `app/lib/stripe.ts`, the actual `getStripe()` client factory used throughout the app — that one is very much live.)

## Gamification-adjacent — `store.actions.ts`, `ratings.actions.ts`

(Full gamification-system context belongs to the gamification-economy-engineer domain; described here only as read from the code.)

- **`store.actions.ts`** — the gem-store purchase flow. `fetchStudentStoreState` surfaces the student's current gem balance, owned/active avatar frames, and perk flags (`studyBoostActive`, `priorityBooking`, `streakFreezes`). `setActiveFrame` verifies frame ownership before equipping. `purchaseStoreItem(itemKey)` checks gem balance against `STORE_ITEMS` catalog cost, then branches update logic by item category: cosmetic frames get appended to a comma-joined `ownedFrames` string (with an "already owned" guard); `study_boost` and `priority_booking` are one-shot boolean flags with an "already active" guard (can't double-purchase while already active); `streak_freeze` **stacks** — explicitly no "already active" gate, since a student can hold multiple freezes at once. Both `study_boost` and `priority_booking` are consumed elsewhere: Study Boost in `create-class-with-pre-auth.ts`, Priority Booking in `create-class-as-student.ts`'s broadcast mode (see `app/lib/classes/README.md`).
- **`ratings.actions.ts`** — the review pipeline that feeds badges/fit-score downstream. `fetchRatingById` computes a simple average; `fetchReviewsById`/`fetchReviewByClassId` fetch review rows. `createReview` validates the caller is the class's own student and the class is `completed`, relies on a DB unique constraint (`studentId_classId`) to reject a second review for the same class (caught and translated to a friendly error rather than a raw constraint message), then awards the student +50 gems and a `feedback_champion` badge, and — only if `rating >= 4` — awards the teacher +75 or +100 sparks (5-star) plus a `top_reviewed` badge on a perfect score.

## General CRUD / profile actions

- **`students.actions.ts`** — `fetchStudentClassHistory` (feeds the fit-score algorithm elsewhere — only `completed` classes, teacher/subject/startTime tuples), `fetchStudents` (admin listing), `fetchStudentsByTeacher` (dedupes a teacher's students across **both** one-off `Class` and `RegularClass` relations into a single `Map`, so a student who's only ever booked a recurring series still shows up in the teacher's student list).
- **`subjects.actions.ts`** — `fetchSubjects` (with a `teacherCount` via `_count`), `fetchSubjectsByName` (substring search), `fetchSubjectsById`, `fetchSubjectsWithTeachers` (only subjects with ≥1 teacher), `fetchSubjectsByTeacherId`.
- **`teachers.actions.ts`** — `fetchTeachersForBooking` is the one used by the booking flow's teacher picker: computes `isAvailable` per teacher via `isWithinAvailability` against the requested slot, then sorts **available-first, then online-first, then alphabetical**. `fetchTeachers`/`fetchTeachersBySubjectsId` are simpler online-first listings. `fetchTeachersExtended` is the admin-facing shape (subjects, availability days, Connect status). `toggleTeacherOnline`/`getTeacherOnlineStatus` manage the online flag that broadcast-mode booking checks (`create-class-as-student.ts` requires ≥1 online teacher for the subject).
- **`users.actions.ts`** — generic `fetchUsers`/`fetchUserById`/`fetchUserByEmail` (the latter eagerly includes `classesAsStudent`, `classesAsTeacher`, and both game profiles — a fairly heavy include used widely as the de facto "get the current user" helper across other action files via `fetchUserByEmail`). Badge fetchers (`fetchAllBadges`, `fetchEarnedBadges`). `updateProfile` is the single handler behind both the student and teacher profile-edit forms (differentiated by which optional fields are present in the payload); it includes a one-time +150 spark reward the first time a teacher completes their profile, guarded by a `teacherGameProfile.profileCompleted` flag and wrapped in its own `try/catch` so a gamification hiccup can't block the profile save itself from succeeding.
- **`onboarding.actions.ts`** — `completeOnboardingTour` marks the one-time welcome-tour modal as seen; explicitly revalidates both dashboard paths because otherwise the client Router Cache could keep serving the pre-flip RSC payload and the tour would reappear on the very next visit despite the DB already being updated.
- **`avatar.actions.ts`** — `saveAvatarOptions` validates the incoming JSON via `parseAvatarOptions` (from `app/lib/avatar-utils.ts`) before persisting, and revalidates both roles' profile and dashboard paths.

## `app/lib/actions/teachers/` subdirectory

Folded into this README rather than given its own file — both are small, teacher-specific actions that logically extend `teachers.actions.ts` but were pulled into their own directory rather than growing that already-large file further.

- **`delete-teacher.ts`** — `deleteTeacherById` (default export). Admin teacher-removal: deletes dependent `TeacherSubject` and `TeacherRating` rows first to avoid FK constraint failures, then deletes the `User` row itself. **Deliberately has no `redirect()`** — its inline comment explains why: it's invoked directly from a client component's `onClick`, not a `<form action>`; `redirect()` works by throwing a special Next.js control-flow error, and a caller wrapping this in its own `try/catch` (reasonable for a delete action) would swallow that throw and silently break the navigation. The client navigates itself afterward via `useRouter().push()` instead.
- **`update-teacher-subjects.ts`** — `updateTeacherSubjects(subjectIds)`, auth-gated to the teacher themself. Full-replace pattern: `deleteMany` whatever's no longer in the new list, `createMany` with `skipDuplicates: true` for whatever's new (duplicates being subjects already associated) — same "diff via delete-then-recreate" shape as `setAvailability` above, just without wrapping it in an explicit `$transaction`.

## Cross-cutting notes

- **`teacherId` nullability**: `Class.teacherId` is nullable (broadcast requests before a teacher claims them). Every function in this directory that selects `class.teacher` either null-checks it in its mapping (`cls.teacher ? formatUser(cls.teacher) : null`) or only runs on rows guaranteed to have a teacher (post-claim). Grep for `.teacher.` access when refactoring and confirm the guard is still there.
- **Authorization coverage is inconsistent** across this directory — some actions (`cancelClassCore`, `acceptClassById`, `refuseClassById`, `proposeCounterOffer`) have an explicit `isParticipant` check; others (e.g. several fetchers, `acceptRegularClass`'s teacher-or-admin check) vary in strictness. Don't assume a given action is safe against an arbitrary id from an unauthenticated or wrong-role caller without checking that specific function.
- **The shared-core-with-worker pattern** recurs across at least four domains in this app: refund expiry (`expire-refund-request.ts` / `expire-refund-requests.actions.ts` reuse it lazily), regular-class materialization (`materialize-occurrences.ts`, called from both `acceptRegularClass` here and the worker), class completion (`completeClass` here and `markCompletedClasses` in the worker, both using the same compare-and-swap idiom against the same `status` transition), and payouts (`payouts.ts` vs. `payouts.actions.ts`). If you're adding a new background-sweepable behavior, follow this split rather than inlining the logic only in a server action.
