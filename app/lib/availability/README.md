# app/lib/availability

A single pure function, `isWithinAvailability`, that answers "is this teacher free at this time?" against their configured weekly schedule. It's the one enforcement point for availability that must stay consistent across every booking path in the app.

## Key file

- **`check-availability.ts`** — exports `isWithinAvailability(slots, startTime, durationInHours, timezone = "UTC")`. Deliberately has *no imports* ("Pure availability checker — no imports, safe to use on client and server," per its header comment), so it can run in a form's client-side pre-filter as well as server-side re-validation without pulling in Prisma or auth — `timezone` conversion is done via the native `Intl.DateTimeFormat` API rather than a library, to keep that constraint.
  - **Timezone-aware as of 2026-08-05 (#128).** `TeacherAvailability` slots are plain `dayOfWeek`/`startHour`/`startMin` integers with no timezone of their own — they mean whatever timezone the teacher was looking at when they painted the grid (see `app/ui/main/availability/README.md`'s new timezone selector). `startTime` is always a real UTC instant. Before this fix, the function read `startTime`'s day/hour/minute via `Date.getDay()`/`getHours()`/`getMinutes()`, which use the *server's* local timezone (confirmed UTC in this deployment) — so the comparison only happened to be correct for a teacher who also happened to be in UTC. The fix: convert `startTime` into `timezone`'s local calendar terms (`toZonedParts`, an internal helper using `Intl.DateTimeFormat(..., {timeZone, hourCycle: "h23"})`) before building the day/hour/minute key to look up — this also correctly shifts the matched day-of-week across a date boundary (e.g. 23:30 UTC can be the *next* day in a timezone ahead of UTC). The `timezone` param defaults to `"UTC"` only so any caller that predates this fix (there shouldn't be any left — see call sites below) degrades to the old behavior instead of silently breaking.
  - A class is "within availability" only if **every 30-minute block it occupies** has a matching slot. It builds a `Set` of `"dayOfWeek-startHour-startMin"` keys from the teacher's saved slots, then walks the requested window in 30-minute increments checking each block is in that set. This means availability slots are assumed to be stored as discrete 30-minute blocks (not open time ranges) — a slot list with gaps mid-range will reject a class that spans the gap.
  - **`slots.length === 0` → always returns `true`.** A teacher who hasn't configured any `TeacherAvailability` rows is treated as always-available. This is called out explicitly as deliberate ("they haven't configured their schedule yet"), not a bug — if a user reports "availability isn't being enforced" for a specific teacher, check whether that teacher simply has zero rows before assuming something is broken.
  - `dayOfWeek` follows JS `Date.getDay()` convention: `0 = Sunday … 6 = Saturday`.

## How it fits together

Called from **four** places (previously documented here as three — that was stale, `fetchTeachersForBooking` was always a real caller, just missed), all of which must stay in sync with each other since this is the actual enforcement layer (not just a UI filter). Each now selects the teacher's `timezone` column alongside their availability rows and passes it through:
1. `app/lib/classes/create-class-as-student.ts` (specific-teacher booking)
2. `app/lib/classes/create-class-with-pre-auth.ts` (pre-authorized booking, where the comment notes this call is "defence in depth" — the primary check already happened client-side and in the API route below)
3. `app/api/payment-intent/pre-auth/route.ts` (server-side re-validation before creating the Stripe pre-auth PaymentIntent) — **this is the actual enforcement point**, not the client-side filter that runs first to shape the UI. Never remove this server-side re-check even though it looks redundant with the client filtering.
4. `app/lib/actions/teachers.actions.ts`'s `fetchTeachersForBooking` — computes each candidate teacher's `isAvailable` flag for the booking-flow teacher picker (UI filtering/sorting, not an enforcement point on its own — the three above are what actually gate a booking).

The slot data itself (`TeacherAvailability` rows) is managed by `app/lib/actions/availability.actions.ts`'s `setAvailability`, which does a full delete-then-recreate of a teacher's slots inside one transaction (see the `app/lib/actions` README) — `isWithinAvailability` just reads whatever rows currently exist, it has no awareness of how they got there. `setAvailability` now also (optionally) updates `User.timezone` in that same transaction, validated via a small `isValidTimezone` check (`Intl.DateTimeFormat` throws on a bogus IANA string) before anything is written.

## Gotchas

- Don't confuse "no slots" (always available) with "explicitly unavailable" — there's no way in this function to represent a teacher who has configured availability but is unavailable for a given range outside it versus one who simply never set anything up. Both look like "no restriction" only in the zero-rows case; any non-empty slot list is a strict allow-list.
- This function has no knowledge of existing booked classes — that's a separate concern handled by `teacherHasSchedulingConflict` in `app/lib/classes/check-teacher-conflict.ts`. A time can pass `isWithinAvailability` and still be rejected for conflicting with an already-scheduled class.
- `User.timezone` defaults every pre-existing row (and any future row without an explicit value) to `"Europe/Lisbon"` — a judgment call based on the app's apparent primary market, not a certainty. A teacher whose actual timezone differs and who never visits the availability page to correct it will have their slots silently misinterpreted exactly the way *every* teacher's were before this fix, just for a smaller set of people instead of all of them. There's no way to distinguish "really is in Lisbon" from "never corrected the default" from the data alone.
- `handleSlotClick` in `app/ui/main/availability/teacher-availability-view.tsx` (the student-facing "click to pre-fill a booking" flow) still uses the *browser's* local time to interpret a clicked slot, not the teacher's timezone — a known, deliberately-deferred gap, not an oversight. See that file's inline comment and its README for why this is UX-only, not a validation bypass.
