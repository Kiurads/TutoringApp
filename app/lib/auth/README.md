# app/lib/auth

Server-side logic for authentication and account lifecycle: login, both registration flows, password change/reset, email verification, and the shared rate-limiting/lockout primitives they all lean on. Everything here is a `"use server"` action or a plain helper called from one — none of it is UI.

Session/role wiring itself (JWT shape, route guarding) lives in `auth.ts` / `auth.config.ts` / `middleware.ts` at the repo root, not here — this directory is what those files call into (`verifyCredentials`, `applyPasswordStalenessCheck`) plus the standalone account-management actions.

## Key files

- **`authenticate.ts`** — `authenticate()`, the server action behind the login form. Rate-limits by IP (flat) and by email (escalating lockout, see below) before ever calling `signIn`. Calls `signIn("credentials", { ...formData, redirect: false })` deliberately — passing `redirect: false` stops NextAuth from doing its own internal redirect (which would otherwise just bounce back to the Referer, i.e. `/login`). **There used to be a real bug here**: an earlier version redirected to a nonexistent `/dashboard`, then a later fix redirected to `/` via the server action — both were flawed because a Server Action `redirect()` drives Next's client router, which can serve a stale cached logged-out `/` from the prefetch cache and strand the user before middleware ever re-evaluates. **This is already fixed** (see git history: `2209626`, then properly in `9df49b6`) — the action now returns `undefined` on success and does no redirect at all; `LoginForm` does a full `window.location.href = "/"` navigation instead, guaranteeing a fresh request that carries the session cookie through `middleware.ts`. Don't reintroduce a `redirect()` call here.
- **`verify-credentials.ts`** — `verifyCredentials(email, password)`, called from `authorize()` in `auth.ts`. Timing-safe against account enumeration: a hardcoded `DUMMY_PASSWORD_HASH` is compared against when no user is found, so `bcrypt.compareSync` always runs regardless of whether the email exists — otherwise a nonexistent-account login fails near-instantly while a wrong-password one takes full bcrypt time, leaking account existence via response timing. Returns `null` for both "no such user" and "wrong password"; callers must not distinguish the two. Also computes `teacherPreferencesSet` (`teachingStyle !== null` for teachers, `true` for everyone else) which flows into the JWT and drives the teacher-onboarding redirect in `auth.config.ts`.
- **`rate-limit.ts`** — In-memory (per-process, `Map`-backed) rate limiting, two flavors:
  - `rateLimit(key, limit, windowMs)` — flat fixed window. Used for IP-based limits (registration, password reset, change-password) where escalation doesn't make sense.
  - `escalatingLockout(key, limit, windowMs)` — used only for login-by-email. Exhausting the window locks the key out for `windowMs * 2^lockoutLevel` (capped at level 6, i.e. 64x), with the level persisting across lockouts instead of resetting — sustained guessing against one account gets progressively slower, not just delayed by a fixed amount. Level decays back to fresh after 24h of inactivity (`LOCKOUT_DECAY_MS`). `clearLockout(key)` must be called on successful login so a legitimate user's own typos don't count against their next attempt (`authenticate.ts` does this).
  - **Known limitation, by design**: state lives in process memory only. Resets on every deploy/restart, and if ever horizontally scaled to >1 instance, each instance tracks its own counters — the effective limit becomes `limit * instanceCount`. Fine for a single-instance deploy; would need Redis or similar otherwise.
  - `getClientIp()` reads `x-forwarded-for`/`x-real-ip`, falling back to `"unknown"` (still rate-limited, just as one shared bucket) when there's no proxy in front (e.g. local dev).
- **`register-student.ts`** — `registerStudent()`. Manual validation (no Zod — see repo-wide convention), bcrypt-hashes the password, creates a `User` with default `role: student`, fires a best-effort verification email (`verification.ts`), redirects to `/login`. Rate-limited per IP, 8 attempts / 10 min.
- **`register-teacher.ts`** — `registerTeacher()`, reached only from the admin-only `/main/admin/teachers/create` page (see `app/main/admin/teachers/README.md`), but it re-checks `auth()` and `role === "admin"` itself rather than trusting the page/middleware — same "self-check identity inside the action" convention used elsewhere in the codebase. Beyond validation, it bulk-assigns `TeacherSubject` rows via `createMany({ skipDuplicates: true })`. **No external side effects beyond the DB and the verification email** — despite what you might expect from this directory's history (see Gotchas below).
- **`request-password-reset.ts`** / **`reset-password.ts`** — Standard token-based reset flow via the `VerificationToken` table, scoped by a `purpose` column (`PASSWORD_RESET` vs `EMAIL_VERIFICATION` share the same table — every lookup filters by `purpose` so a verification token can never be redeemed as a reset token or vice versa). `requestPasswordReset` always returns the same generic success message regardless of whether the account exists, to avoid leaking account existence; it only actually sends the email if a user is found. `resetPassword` consumes (deletes) the token unconditionally before checking expiry, so a used/expired token can never be redeemed twice, and stamps `passwordChangedAt` on success. Both rate-limited per IP; the request side is also rate-limited per email.
- **`change-password.ts`** — `changePassword()`, authenticated in-app password change. Requires `auth()`, verifies the current password with `bcrypt.compare` (async, unlike `verify-credentials.ts`'s `compareSync` — see Gotchas), rate-limits by `${userId}:${ip}` since this is an authenticated action against a known account. Stamps `passwordChangedAt`.
- **`session-staleness.ts`** — `applyPasswordStalenessCheck(token, dbPasswordChangedAt)`, a pure function pulled out of `auth.ts`'s `jwt` callback so it's unit-testable without instantiating NextAuth/Prisma. Compares the JWT's stamped-at-login `passwordChangedAt` against the live DB value; mismatch sets `token.invalidated = true`. The `session` callback in `auth.config.ts` checks that flag and strips the user from the session entirely — this is what makes `changePassword`/`resetPassword` invalidate *every* outstanding session for that account, not just rotate a token.
- **`verification.ts`** — `createAndSendVerificationEmail(email)`. Creates a `VerificationToken` (`purpose: EMAIL_VERIFICATION`, 24h TTL) and emails a link to `/api/auth/verify` (see `app/api/auth/verify/README.md`). Always best-effort: every error is caught and logged internally, never thrown, because both registration paths call this *after* the `User` row is already committed — a Resend outage must not roll back or fail a successful registration.

All ten files have `.test.ts` siblings with substantial coverage (validation edge cases, rate-limit/lockout behavior over simulated time, timing-safety of `verifyCredentials`, token `purpose` scoping, `passwordChangedAt` stamping). Check those first before assuming behavior not documented here.

## How it fits together

- `auth.ts` (`authorize()` callback) calls `verifyCredentials`, then separately flips `isOnline: true` on the `User` row itself when `role === "teacher"` — that side effect lives in `auth.ts`, not in this directory, and login is the *only* thing that marks a teacher online (no heartbeat/presence system).
- `auth.config.ts`'s `jwt` callback stamps `role`, `teacherPreferencesSet`, and `passwordChangedAt` onto the token at sign-in; `auth.ts`'s own `jwt` callback (Node runtime only) layers `applyPasswordStalenessCheck` on top for every subsequent request, doing a live Prisma lookup that `auth.config.ts` can't do (it's also loaded by Edge-run `middleware.ts`).
- Both registration actions funnel through `verification.ts` and `rate-limit.ts`; both password-mutating actions (`change-password.ts`, `reset-password.ts`) stamp `passwordChangedAt`, which is what `session-staleness.ts` checks.
- `app/ui/login/*` and `app/ui/register/**/*` forms call these actions via `useActionState`.

## Gotchas / non-obvious conventions

- **No Zod, anywhere.** All validation here is manual (regex, length checks, field presence). Don't introduce Zod as a one-off for a new auth form without discussing — it'd be inconsistent with every existing file in this directory.
- **bcrypt sync vs async, deliberately different per call site**: `verify-credentials.ts` uses `bcrypt.compareSync` (needs to run unconditionally against a dummy hash for timing safety — sync keeps that simple), while `change-password.ts` uses the async `bcrypt.compare`/`bcrypt.hash`. This split is intentional per-file, not an inconsistency to "fix" — check what a given file already does before adding a new bcrypt call to it.
- **The Nextcloud integration described in older docs/agent context no longer exists.** Git history (`103ed67 chore: remove Nextcloud integration`) shows it was removed from `register-teacher.ts`. A brief successor — auto-creating a Stripe Connect account at registration — was also added (`93ac7a0`) and then deliberately reverted in favor of *lazy* account creation on first payout-onboarding click (`e9e0067 fix Stripe Connect onboarding always failing on first attempt`, which explicitly "drops eager Stripe Connect account creation at teacher registration in favor of lazy creation"). **Current `register-teacher.ts` has no external side effects at all** beyond the DB writes and the best-effort verification email — if you're told otherwise, re-read the file, don't trust stale context.
- **`VerificationToken.token` isn't `@unique` on its own** — only the `[identifier, token]` composite is — so both `reset-password.ts` and `app/api/auth/verify/route.ts` look tokens up with `findFirst`, not `findUnique`, and both scope by `purpose` for the reason above.
- **Rate limiting resets on deploy and doesn't share state across instances** — see `rate-limit.ts` notes above. Don't assume it's a durable/distributed guarantee.
- `authenticate.ts`'s comment block is worth reading in full if you touch it — it explains both the escalating-lockout rationale and the redirect history in more depth than is repeated here.
