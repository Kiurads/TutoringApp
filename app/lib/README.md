# app/lib

Server-side business logic and shared utilities for the whole app. This directory has two layers:

- **Subdirectories** — each is a focused domain module with its own README (linked below); most contain "use server" Server Actions or pure helper functions scoped to one feature area.
- **Top-level files** (this README) — a flat grab-bag of cross-cutting engines that don't have a subdirectory of their own: gamification/economy, Stripe payouts, notifications, and email. These are consumed from many places across `app/lib/actions/**`, `worker/src/**`, and UI components, so they're documented here rather than duplicated per-consumer.

## Subdirectories

| Directory | Covers |
|---|---|
| `actions/` | The Server Actions hub — ~25 files spanning nearly every domain (classes, payments, store, users, subjects, teachers, etc.), plus `actions/teachers/`. See its own README for the full breakdown. |
| `auth/` | Login, registration, password reset/change, rate limiting, session staleness. |
| `availability/` | Teacher availability conflict checks. |
| `classes/` | Class booking/pricing/creation primitives (pre-auth vs. immediate-capture paths, Jitsi room generation, teacher-conflict checks). |
| `refund-requests/` | The auto-expiry side of the `RefundRequest` no-show/dispute workflow. |
| `regular-classes/` | Recurring-class occurrence materialization (the watermark/`lastMaterializedThrough` mechanism). |
| `subjects/` | Admin subject creation. |
| `teachers/` | Fit-score ranking and client-side teacher-list sorting. |
| `types/` | Client-safe TypeScript shapes that Server Actions map Prisma rows into, with the Decimal-conversion conventions used across the app. |

## Top-level files

### Gamification / economy

- **`gamification.ts`** — the single write-path for all currency/badge/streak mutations. `awardGems`/`awardSparks` clamp at 0, diff old/new tier or rank via `calcTier`/`calcRank`, and fire a `tier_up`/`rank_up` notification only on an *increase* (a negative/reversal amount can lower a tier without spamming a "congratulations" notification). `reverseClassPoints` is an idempotent refund clawback, guarded by a `pointsReversed` flag on `Class`, that reverses exactly what a given class actually granted (tracked via running `gemsAwarded`/`sparksAwarded` totals) rather than a guessed fixed amount. `awardBadge` is idempotent via the `@@unique([userId, badgeId])` constraint. `checkSessionBadges` awards milestone badges by completed-class count. `updateActivityStreak` is DB glue around the pure `computeStreakUpdate` state machine in `gamification-utils.ts` — split out because a `"use server"` file requires every export to be async, while the streak branching logic needs to stay synchronous to unit-test without a database. `maybeAwardLuckyBonus` is a 10%-chance always-positive bonus, deliberately built without loot-box-style rarity tiers. Gotcha: awarding the `engaging_educator` badge for reaching mentorship rank 3 (Elite Mentor) happens inline inside `awardSparks`, not in `checkSessionBadges` — easy to miss if you're only looking for badge logic in the badge-checking function.
- **`gamification-utils.ts`** — pure, DB-free utilities: `TIER_THRESHOLDS`/`RANK_THRESHOLDS` (both `[0, 500, 1500, 3500, 7500]`) and their name/progress helpers (`calcTier`, `calcRank`, `getTierProgress`, `getRankProgress`); `getWeekStart` (Monday 00:00 **UTC** of the containing week — deliberately UTC-anchored rather than server-local time, so streak/quest boundaries are stable regardless of deploy region); and `computeStreakUpdate`, the actual weekly-streak state machine (`first_activity` / `already_counted` / `continued` / `broken`, with freeze-consumption logic — a freeze covers exactly one skipped week, i.e. `weeksDiff === 2`).
- **`quests.ts`** — a small, fixed (non-admin-configurable) weekly quest system, deliberately minimal per an inline comment citing "purpose over points." Two student quests (`weekly_2_classes` +30 gems, `weekly_leave_review` +15 gems) and one teacher quest (`weekly_3_classes` +30 sparks). `fetchWeeklyQuests()` computes progress *live* from `Class`/`TeacherRating` rows scoped to the current week (progress is never stored); `claimWeeklyQuest(questKey)` re-derives progress server-side rather than trusting the client, then creates a `QuestClaim` row — the `@@unique([userId, questKey, weekStart])` constraint is the only thing making claims idempotent (a failed create is interpreted as "already claimed").
- **`store-catalog.ts`** — `STORE_ITEMS: StoreItem[]`, the static source of truth for gem-store prices/keys: three cosmetic avatar frames (`frame_scholar` 300g, `frame_luminary` 800g, `frame_sage` 2000g) and three consumables (`study_boost` 200g, `priority_booking` 250g, `streak_freeze` 150g — note `streak_freeze` isn't gated by an "already owned" check the way the frames are, so freezes can stack).
- **`avatar-utils.ts`** — free, no-gem-cost DiceBear "toon-head" avatar customization, entirely separate from the frame-purchase system above. `AvatarOptions` + `VALID_*` allow-lists per field; `sanitize()` falls back to `DEFAULT_OPTIONS` per-field for anything invalid (hex color fields are exempt — any 6-digit hex passes); `buildAvatarDataUri` generates the SVG locally via `@dicebear/core` with no network call (preferred everywhere per the file's own comment); `buildAvatarUrl` is the network/URL-param equivalent for cases that need a URL rather than inline data; `parseAvatarOptions` safely parses the DB-stored JSON string, returning `null` on failure rather than throwing.
- **`frame-utils.ts`** — small pure-function helpers for the store's cosmetic frames: `parseOwnedFrames` (splits the comma-separated `ownedFrames` string — the canonical parser, though a couple of call sites in `actions/store.actions.ts` and the store page inline the same split logic instead of importing this), `getFrameClass` (frame key → CSS class defined in `globals.css`), `getFrameLabel`, `getFrameColor`. Only three frame keys are hardcoded here (`scholar`/`luminary`/`sage`) — there's no single shared constant for the frame-key list; it's independently duplicated in `store-catalog.ts` and again in `app/main/student/store/page.tsx`.

### Stripe / payouts

- **`stripe.ts`** — the server-side Stripe client factory (`import "server-only"` guarded). `getStripe()` lazily constructs a module-level `Stripe` singleton on first call rather than at import time, specifically because Next.js imports every route module during `next build` to collect page data — constructing the client eagerly at module scope would crash any build without `STRIPE_SECRET_KEY` set. Every route handler that needs Stripe (`payment-intent`, `pre-auth`, `setup-intent`, `webhooks/stripe`) calls `getStripe()` inside its handler for this reason. **Gotcha**: this discipline isn't followed everywhere — `payouts.ts` (below) and `refund-requests/expire-refund-request.ts` both construct `new Stripe(...)` directly instead of calling `getStripe()`, so the singleton isn't actually shared across the whole app despite the intent.
- **`payouts.ts`** — the Stripe Connect payout engine. `transferPayoutForClass(classId)` is called from both the manual "Mark Complete" UI path (`classes.actions.ts`) and the worker's automated poller (`worker/src/complete-classes.ts`) when a class transitions to `completed`; idempotency between the two callers is a compare-and-swap `updateMany` on `Payment.payoutStatus` (whichever caller's update actually affects a row proceeds to call Stripe), not a lock or transaction. `transferPendingPayoutsForTeacher(teacherId)` sweeps a teacher's backlog of accrued-but-unpaid payouts once their Connect account goes active (called from the `account.updated` webhook). `ensureConnectAccount(user)` idempotently creates a Stripe Express account shell, called both at teacher registration (best-effort) and again from Connect onboarding as a no-op-if-exists fallback. Synchronous Stripe errors are caught and recorded (`payoutStatus: "failed"`); *asynchronous* failures (a transfer that succeeded then got reversed later) are handled separately by the `transfer.reversed`/`charge.dispute.closed` webhook handlers, not here.
- **`payouts-utils.ts`** — pure functions only, no Stripe calls (explicit "no server action directive needed" comment). `computeCommissionSplit(amount, feeRateBps = DEFAULT_PLATFORM_FEE_BPS)` where `DEFAULT_PLATFORM_FEE_BPS = 1500` (15%). Rounds from total cents first so the platform-fee and teacher-payout halves always sum back to exactly the original amount — never off by a rounding cent. Takes an optional rate override specifically so a future tier-based commission discount (e.g. tied to `TeacherGameProfile.mentorshipRank`) is a call-site change, not a rearchitecture — that tiering doesn't exist yet.

### Notifications

- **`notifications.ts`** — a single-export file, `createNotification(userId, type, title, body, link?)`, a thin wrapper around `prisma.notification.create`. The `NotificationType` enum has ~28 values spanning every domain (class lifecycle, gamification, counter-offers, refund disputes, recurring classes, payouts). Called synchronously and inline from nearly every mutating Server Action across the app — there's no queue or async dispatch; creating a notification is just another `await` alongside the state change it documents. Consumed via `app/lib/actions/notifications.actions.ts` (read/mark-read API) and rendered by `app/ui/main/notifications/notification-dropdown.tsx`, which polls every 20 seconds (paused while the tab is backgrounded) to approximate live updates in the absence of a websocket/SSE layer.

### Email

- **`email.ts`** — a thin wrapper around the Resend SDK for transactional email. `RESEND_API_KEY` is required for a real send; if it's missing, the function logs the email's subject/body/link to the console instead of throwing, so registration/password-reset flows stay testable without a Resend account and a missing key never breaks the underlying action. All sends are explicitly best-effort — callers never let an email failure fail the action that triggered it. Four exports: `sendVerificationEmail`, `sendPasswordResetEmail` (both called from `app/lib/auth/**`), and two operator-facing alerts with no in-app notification equivalent — `sendDisputeAlertEmail` (a Stripe dispute needs a human in the Stripe dashboard before the evidence deadline; nothing in-app can act on it) and `sendPaymentIssueAlertEmail` (a failed capture or auto-expired pre-auth needs manual reconciliation). Note there's an unrelated, unused React Email component at the top-level `/email/` and `/app/email/` directories (duplicated in both, byte-identical) — this file does **not** use either; it builds raw HTML template strings instead. See those directories' own READMEs.
