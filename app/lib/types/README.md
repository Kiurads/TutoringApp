# app/lib/types/

Hand-written TypeScript interfaces describing the shapes server actions return to client components. **None of these are generated from `prisma/schema.prisma`** — Prisma's own generated types (`Prisma.ClassGetPayload<...>`, etc.) are used internally inside `app/lib/actions/*.actions.ts`, but the types here are the deliberately-simplified, client-safe *output* shapes those actions map Prisma rows into before returning them. After any change to `prisma/schema.prisma`, these files have to be updated by hand — there is no codegen step keeping them in sync, and the codebase has drifted before.

## Why this layer exists: the Decimal problem

MySQL money/decimal columns (`pricePerHour`, `totalPrice`, `durationInHours`, `amount`, `rating`, …) come back from Prisma as `Decimal` instances (from `decimal.js`), not plain numbers. `Decimal` doesn't serialize through `JSON.stringify` the way a server action's return value needs to when crossing the server/client boundary — and Next.js server actions require plain serializable data anyway. Every type in this directory that stands in for a Decimal-bearing Prisma model represents that field as `string` or `number`, and the corresponding action does the conversion explicitly before returning. Two conversion patterns are used, chosen per field by what the value is *for*:

- **Display formatting → `string` via `.toFixed(2)`**: used for money meant to be shown, not computed on further — e.g. `pricePerHour` and the averaged `rating` in `app/lib/actions/teachers.actions.ts` (`teacher.pricePerHour ? teacher.pricePerHour.toFixed(2) : "0.00"`; ratings default to the literal string `"No Reviews"` when a teacher has none, which is why `TeacherDetails.rating` is typed `string`, not `number`).
- **Raw passthrough → `string` via `.toString()`**: used for `Class.totalPrice`/`durationInHours` in `ClassData`/`ClassDataSimple` (`app/lib/actions/classes.actions.ts`) — preserves full precision as a string rather than rounding for display, left for the UI layer to format.
- **Arithmetic → `number` via `.toNumber()`**: used wherever the value needs to be computed on further, either before formatting (rating averages are summed with `.toNumber()` across all reviews, then divided, then `.toFixed(2)`'d only at the end) or for real math (e.g. commission-split calculations use `Number(cls.totalPrice)`, `cls.durationInHours.toNumber()` feeds `decimalToHours()` and end-time math). `Rating.rating` in `ratings.types.ts` is typed `number` for exactly this reason — it's an individual review's Decimal converted once via `.toNumber()`, with no display-formatting step, since `ratings.actions.ts` hands it back raw for the UI to format itself.

There's no shared `decimalToString`/`decimalToNumber` helper in this directory or a common `app/lib` location — each `*.actions.ts` file does the `.toFixed(2)` / `.toString()` / `.toNumber()` call inline at the point it builds the return object. `decimalToHours()` (used for `durationInHours`) is defined locally inside `classes.actions.ts`, not shared. When adding a new Decimal-bearing field to a type here, check the sibling fields in the same interface for which convention that type already uses, and match it rather than picking a third pattern.

## Files

- **`classes.types.ts`** — `Class` model output shapes.
  - `ClassData` — full detail-page shape: nested `teacher`/`student` (`UserDetails`, teacher nullable per the schema's broadcast-request design), `status`/`subject` as plain strings (not the Prisma enum/relation), `durationInHours`/`totalPrice` as raw `.toString()` decimal strings, `counterOfferTime`/`jitsiRoom` nullable.
  - `ClassDataSimple` — a slimmer variant without the nested user/subject objects, for list contexts that don't need them.
  - `BookedClass` — the shape used by booked-classes tables; trims `teacher`/`student`/`subject` down to `{ name }` only, adds `requestedBySelf` (derived, not a DB column — computed by the action from `requesterId` vs. the current session user).
- **`ratings.types.ts`** — `Rating`: one `TeacherRating` row, flattened with a denormalized `studentName` (joined server-side so the client doesn't need a second lookup) and `rating: number` (see conversion note above).
- **`regular-classes.types.ts`** — `RegularClassData`: one `RegularClass` template row. Note the doc-comment on `startTime`: it's `"HH:MM"` local time — only the time-of-day portion of the underlying `DateTime` matters, since `dayOfWeek` (not the date part of `startTime`) is the actual recurrence key in the schema.
- **`subjects.types.ts`** — `SubjectData`: `{ id, name, teacherCount? }`. `teacherCount` is optional because it's only populated by the specific query that needs the aggregate (e.g. a subjects-browse list), not by every `Subject` fetch.
- **`teachers.types.ts`** — teacher-facing shapes, both Decimal-bearing fields formatted as display strings (see conversion note above).
  - `TeacherDetails` — base card shape: `rating: string` (formatted average or `"No Reviews"`), `pricePerHour: string` (`.toFixed(2)`, `"0.00"` if unset).
  - `TeacherExtended extends TeacherDetails` — adds `subjects`/`subjectIds` (display names vs. IDs — the split exists because fit-score matching needs IDs while the UI wants names), `availabilityDays: number[]` (unique `dayOfWeek` values, for the same fit-score use), `status: "Active" | "Pending" | "Inactive"` (a derived admin-facing label, not a raw DB column), `fitScore?: number | null`, and `connectStatus` typed as the literal union mirroring the schema's `ConnectStatus` enum values.
- **`user.types.ts`** — the shared user-display shape used across the other type files.
  - `UserDetails` (default export) — `{ id, name, email, role, avatarOptions? }`; `name` is always a precomputed `"${firstName} ${lastName}"`, never split first/last, since most consumers only render a display name.
  - `StudentDetails extends UserDetails` — adds back `firstName`/`lastName`/`phoneNumber`/`activeFrame` for contexts that do need the split name or student-specific fields.
  - `formatUser()` — the one shared helper in this directory; converts a raw Prisma `User`-shaped object (or any object with matching fields) into `UserDetails`, including the `name` join and an `as` cast of the DB's `role: string` into the `"student" | "teacher" | "admin"` literal union. Every other type file that embeds a user (`ClassData.teacher`/`.student`, `RegularClassData.teacher`/`.student`) uses `UserDetails` directly rather than redeclaring an inline shape — this is the one piece of shared/DRY structure in the directory; everything else here is independent per-file interfaces.

## Non-obvious conventions

- Enum-typed Prisma fields (`Status`, `RegularClassStatus`, `ConnectStatus`, `Role`) are widened to plain `string` in most of these interfaces (`ClassData.status`, `RegularClassData.status`, `UserDetails.role`) rather than re-declared as literal unions — `TeacherExtended.connectStatus` and `TeacherExtended.status` are the exceptions, using literal unions. There's no enforced rule for when a type here gets the precise union vs. plain `string`; check the specific interface rather than assuming consistency across files.
- Nullability is preserved faithfully from the schema where it matters to rendering logic — `ClassData.teacher: UserDetails | null` (broadcast requests), `ClassData.counterOfferTime: string | null`, `ClassData.jitsiRoom: string | null` — so a `null` check at the UI layer is meaningful and matches what the DB can actually contain.
- `Date` vs. `string` is inconsistent across files by design intent, not oversight: `BookedClass.startTime` is a real `Date` (consumed by a calendar component that needs `Date` arithmetic), while `ClassData.startTime`/`RegularClassData.createdAt` etc. are pre-formatted `string`s (already serialized for direct display). Match whichever the specific consuming component expects rather than assuming one convention project-wide.
