# app/lib/classes

Pure/small helper functions and the three "create a class" entry points used by class-booking flows. This directory holds the logic that's shared across booking modes (specific-teacher, broadcast, teacher-initiated, pre-authorized) so it isn't reimplemented per call site. The bigger post-creation lifecycle (accept/refuse/cancel/counter-offer/claim) lives in `app/lib/actions/classes.actions.ts`, not here — this directory is specifically about getting a `Class` row *into* existence (plus a couple of small standalone predicates used elsewhere).

## Key files

- **`compute-class-price.ts`** — `computeClassPrice(pricePerHour, durationInHours, studyBoostActive = false)`. The single base-price formula (`pricePerHour * durationInHours`, with an optional 5%-off Study Boost discount rounded to 2dp). The header comment explicitly says this replaced several independent reimplementations that had drifted — only some previously applied the Study Boost discount. `studyBoostActive` defaults to `false` so broadcast/recurring callers that have no notion of the perk get the plain undiscounted price.
  - **Gotcha**: not every call site actually threads `studyBoostActive` through. `create-class-as-student.ts`'s specific-teacher path calls `computeClassPrice(price, durationInHours)` with no third argument (no discount applied), while `create-class-with-pre-auth.ts` looks up `studentGameProfile.studyBoostActive` and passes it. So a student with an active Study Boost gets the discount when pre-authorizing but not when booking a specific teacher without pre-auth — worth flagging as a possible inconsistency rather than an intentional design choice (nothing in the comments explains why the plain path skips it).

- **`check-teacher-conflict.ts`** — `teacherHasSchedulingConflict(teacherId, candidateStart, candidateDurationInHours, excludeClassId?)`. Fetches the teacher's `scheduled` classes and checks time-window overlap in JS. Per its own comment, only `status: "scheduled"` classes count as conflicts — competing `requested` classes for the same slot are expected (a teacher can receive multiple overlapping requests before accepting one), so this is deliberately *not* checked at request-creation time against other requests. Overlap is computed in JS rather than in a Prisma `where` clause because MySQL can't do a typed `(startTime + durationInHours)` comparison — the same approach the comment says is used in `worker/src/complete-classes.ts` for the equivalent problem. `excludeClassId` lets a reschedule/edit path exclude the class being modified from its own conflict check.

- **`can-pay-for-class.ts`** — `canPayForClass({ paid, status, hasPreAuth? })`. A class is payable once `scheduled` or `completed` and not yet `paid`. If `hasPreAuth` is true, returns `false` even if otherwise payable — an outstanding pre-auth hold gets captured automatically on accept (see `acceptClassById` in `classes.actions.ts`), so showing a manual "Pay Now" button while that capture is pending risks a race against it. Per its comment, only `app/main/student/classes/[id]/page.tsx` currently has `hasPreAuth` in its fetched data to pass in; table/list views work off summarized data without it, so they simply omit the argument (preserving prior behavior rather than being an oversight).

- **`generate-jitsi-room.ts`** — `generateJitsiRoom()` returns `ponte-<32 hex chars>` using `crypto.randomBytes(16)`. Deliberately decoupled from the class's own id (per its comment) so video-call room access isn't tied to a primary key that might leak into emails/logs, and so a compromised room name can be rotated independently of the class record.

- **`create-class-as-student.ts`** — `"use server"` action backing the student booking form, in two modes based on whether `teacherId` was submitted:
  - **Specific-teacher mode**: looks up the teacher's `pricePerHour` and `TeacherAvailability` rows, calls `isWithinAvailability` (see `app/lib/availability`) and `teacherHasSchedulingConflict`, computes price via `computeClassPrice` (no Study Boost, see above), creates the `Class` at `status: "requested"`, and notifies the teacher (`class_requested`).
  - **Broadcast mode** (`teacherId` omitted): requires at least one `isOnline: true` teacher covering the subject to exist, else returns an error. Creates the `Class` with `teacherId: null`, `totalPrice: 0`, and stamps `priority: true` if the student's `StudentGameProfile.priorityBooking` is set — then immediately flips `priorityBooking` back to `false` (one-shot consumption of a purchased gem-store perk). **The `priority` flag is stored but never read anywhere for queue ordering** — `fetchOpenRequestsForTeacher` in `classes.actions.ts` orders by `startTime asc` only. This is a known inert feature, not a bug to silently "fix" without discussion.
  - Both modes reject `startTime` earlier than tomorrow (server-side re-validation of a client-side rule).

- **`create-class-as-teacher.ts`** — `"use server"` action for the teacher-initiated booking flow (teacher picks a specific student). Simpler than the student version: no availability or conflict check against the *teacher's own* schedule is performed here (the teacher is presumably choosing their own free slot), price is computed via `computeClassPrice` (no discount parameter — teacher-initiated bookings don't consider Study Boost at all since it's a student perk), `requesterId` is set to the teacher's id, and it notifies the *student* instead. Redirects to `/main/teacher/classes` rather than a classes list with a toast.

- **`create-class-with-pre-auth.ts`** — `createClassWithPreAuth(data, preAuthIntentId)`, a non-`"use server"`-decorated async function (called from an API route context, not as a form action) used by the pre-authorized-payment booking flow. Takes an already-created Stripe PaymentIntent id (`preAuthIntentId`) and stores it on the new `Class` row. Re-checks availability and scheduling conflict even though the comment notes the primary enforcement point is the pre-auth API route (`app/api/payment-intent/pre-auth/route.ts`) — explicitly "defence in depth," not redundant dead code. Does apply the Study Boost discount (reads `studentGameProfile.studyBoostActive`, consumes it after successful creation) — see the price-formula inconsistency noted above. Owned jointly with the stripe-payments-engineer domain; don't change the `Class`-creation shape here without checking that side too.

## How it fits together

All three `create-class-*` functions converge on the same shape: validate → check availability/conflict (where applicable) → `computeClassPrice` → `prisma.class.create` → `createNotification` (from `app/lib/notifications.ts`) → `redirect`. `isWithinAvailability` (imported from `app/lib/availability/check-availability.ts`) and `teacherHasSchedulingConflict` are the two gatekeeping checks reused across the specific-teacher and pre-auth paths; broadcast mode and teacher-initiated mode skip both (broadcast has no teacher yet to check against; teacher-initiated trusts the teacher's own judgment). None of these files import from `app/lib/actions/classes.actions.ts` — the relationship is one-directional (actions layer doesn't call back into these creation helpers either; they're both leaf-level and orchestration-level pieces invoked from UI/API routes).

## Gotchas

- The Study Boost discount inconsistency above (only the pre-auth path applies it).
- `check-teacher-conflict.ts` intentionally ignores `requested` classes — don't "fix" this to also flag pending requests as conflicts without understanding that competing requests are expected until one is accepted.
- `generate-jitsi-room.ts`'s room name is independent of any class id by design — don't derive it from `class.id` in a refactor.
- Tests: `can-pay-for-class.test.ts`, `check-teacher-conflict.test.ts`, `compute-class-price.test.ts`, `create-class-as-student.test.ts`, `create-class-with-pre-auth.test.ts` cover these files thoroughly, including the availability/conflict rejection paths and broadcast-mode edge cases — extend them alongside any logic change.
