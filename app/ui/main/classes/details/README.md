# app/ui/main/classes/details

The widgets that make up a single class's detail page (`app/main/student/classes/[id]/page.tsx` and `app/main/teacher/classes/[id]/page.tsx` both compose from this directory): the summary card, the action buttons/modals, the "mark complete" control, and the Jitsi video-call embed.

## Key files

- **`class-action-modals.tsx`** — the single largest and most reused component in this domain. Role-parameterized (`role: "student" | "teacher"`) rather than forked into two components — both `student-table-buttons.tsx` and `teacher-table-buttons.tsx` (in the parent directory) render this same component with different props, and it's also the direct target of the detail pages themselves. **This role-parameterized-shared-component shape is a deliberate, reused pattern in this codebase** — `app/ui/main/regular-classes/regular-class-action-modals.tsx` is explicitly modeled after it.
  - Renders up to five actions (Accept / Suggest Alternative Time / Refuse / Pay Now / Cancel) gated by boolean props the caller computes (`canAccept`, `canCounterOffer`, `canRefuse`, `canPay`, `canCancel`), each backed by a confirmation `<dialog>` and wired directly to the corresponding server action from `classes.actions.ts` via `useTransition`.
  - **Uses real `<dialog>` elements with `showModal()`/`close()`** rather than a CSS-only `modal-open` class toggle — the inline comment explains this gets focus trapping, Escape-to-close, and focus return to the trigger element for free from the browser. A `useEffect` keyed on the `open` state string imperatively calls `showModal()`/`close()` on the right ref; each dialog's own `onClose` handler syncs `open` back to `null` when the dialog is dismissed natively (Escape key) rather than via one of the component's own buttons — don't remove that handler or Escape-dismissal will desync the state.
  - **Client-side refund-tier preview**: computes `hoursUntil` from `startTime` and renders a `refundNote` in the cancel confirmation dialog mirroring the exact tier thresholds enforced server-side in `cancelClassCore` (`>24h` full refund / `12–24h` 50% / `≤12h` none) — this is a *preview only*; if the server-side tier logic in `classes.actions.ts` ever changes, this copy must be updated to match or the modal will show a stale promise.
  - **Counter-offer banner**: when `role === "student"` and a `counterOfferTime` is present, renders an inline accept/decline banner above the action buttons (not another modal) — this is the surface a student sees the teacher's proposed alternative time on, wired to `acceptCounterOffer`/`declineCounterOffer`.
  - **Pay flow**: `openPay` fetches `POST /api/payment-intent` (the *immediate-capture* PaymentIntent creation route — distinct from the pre-auth route used at booking time) to get a `clientSecret`, then renders `CheckoutForm` (`app/ui/payment/checkout-form.tsx`) inside the pay modal. This is the "Pay Now" surface `canPayForClass` gates the visibility of.
- **`class-info-card.tsx`** — the read-only summary card at the top of a detail page: colored status bar (own small `STATUS_BORDER` map, separate from `class-status-badge.tsx`'s badge-color map — keep both in sync if a new status is added), paid/unpaid badge, student/teacher `UserCard`s (with a distinct "Waiting for a teacher" placeholder state when `classDetails.teacher` is null — broadcast request unclaimed), and a details grid (start time, duration via `decimalStringToHours`, total price — rendered as an italic "TBD" when `totalPrice === "0"`, i.e. an unclaimed broadcast request, and requested-on date).
- **`complete-class-button.tsx`** — calls `completeClass` (`classes.actions.ts`) via `useTransition`, then `router.refresh()` on success (no redirect — `completeClass` doesn't call `redirect()`, it returns `{}` or `{ error }`, so the button is responsible for refreshing the page itself to reflect the new `completed` status). Surfaces a server-side error (e.g. "Class hasn't ended yet.") inline.
- **`jitsi-embed.tsx`** — lazily loads the Jitsi Meet external API script (`meet.jit.si/external_api.js`), reusing an already-in-flight `<script>` tag if one exists rather than injecting a duplicate, then constructs a `JitsiMeetExternalAPI` instance into a container ref. Cleans up via `api.dispose()` on unmount, with a `cancelled` flag guarding against the async script-load resolving after the component has already unmounted.
- **`join-class-card.tsx`** — gates the video-call embed behind a join window: only renders anything if `status === "scheduled"` and a `jitsiRoom` exists; shows a "join" button only within `[start - 10min, end + 5min]` (re-checked every 30s via `setInterval`, not just once on mount, so the button appears/disappears live without a page refresh). Loads `JitsiEmbed` via `next/dynamic` with `ssr: false` (the Jitsi API is a browser-only global). Once joined (`joined` state), the embed replaces the join button and stays mounted rather than re-checking the window — a class that's joined right at the edge of the window won't be booted mid-call.
- **`message-thread.tsx`** — scoped 1:1 messaging for a single class, backed by `app/lib/actions/messages.actions.ts` and the new `Message` model. Deliberately anchored to a specific booking rather than a general student↔teacher inbox (matches how trust-and-safety-minded competitors like Outschool/Wyzant keep coordination tied to a booking, not open-ended contact — see issue #91's research). Only rendered once `classData.teacher` is non-null (both detail pages gate on this — nobody to message before a teacher's assigned). Polls every 15s (visibility-aware, same pattern as `notification-dropdown.tsx`) rather than using a websocket, since this app has no push-update server. No per-message read tracking — the existing `message_received` notification already covers the "something new" signal, so the thread itself stays a simple ordered log via daisyUI's `chat`/`chat-bubble` classes.

## How it fits together

Every mutating action in this directory funnels through `app/lib/actions/classes.actions.ts` — no local state mutation beyond UI concerns (modal open/closed, form field values). The one exception is the payment sub-flow, which talks to `/api/payment-intent` (an API route, not a server action) because Stripe Elements needs a `clientSecret` obtained via `fetch`, not something a server action can hand back synchronously into a form submission the way the other actions work.

## Gotchas

- The cancel modal's `refundNote` text is a hand-maintained mirror of server-side refund-tier logic — a common source of copy/logic drift if only one side is updated.
- `class-info-card.tsx`'s `STATUS_BORDER` map and `class-status-badge.tsx`'s color map are two independent mappings of the same `status` string to a color — check both when adding a new `Class.status` value (e.g. `cancelled` is present in the badge map's error-color branch but absent from `STATUS_BORDER`, which falls back to `bg-base-300` for any unmapped status including `cancelled`).
- `complete-class-button.tsx` relies on `router.refresh()` rather than a `redirect()` — if this component is ever reused somewhere the page doesn't automatically reflect fresh server data on refresh, the button will appear to succeed without visibly updating the class status.
