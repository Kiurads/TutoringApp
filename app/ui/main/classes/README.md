# app/ui/main/classes

The UI layer for the class-booking domain: the "My Classes" tables (student and teacher variants), the open-broadcast-requests panel, status/paid indicators, and the no-show/review widgets shown on a class's detail page. Almost everything here is a thin presentational wrapper around data already shaped by `app/lib/actions/classes.actions.ts` — this directory has very little of its own business logic, deliberately reusing helpers like `canPayForClass` rather than reimplementing payability rules in JSX.

Subdirectories: `create/student/` and `create/teacher/` (the two booking forms — own README each), `details/` (the class detail-page widgets — own README), and `review/` (folded into this README below — a single file).

## Key files

- **`classes-table.tsx`** — a simple read-only table (used in admin-style contexts), no actions, no filtering. Shows `"Unassigned"` for a null `teacher` (broadcast request not yet claimed) and a Yes/No paid badge.
- **`class-status-badge.tsx`** — maps `Class.status` to a daisyUI badge color: `completed` → success, `scheduled` → info, `refused`/`cancelled` → error, everything else (`requested`) → warning. Purely presentational, no logic beyond the color map — extend this if a new status value is ever added.
- **`add-class-button.tsx`** — a plain link to `/main/student/classes/request`. (Note: `teacher-booked-classes.tsx` actually imports its own separate `create/teacher/add-class-button.tsx`, not this one — see the `create/teacher` README.)
- **`first-visit-warning.tsx`** — a `"use client"` dismissible banner gated on `localStorage.getItem("hasDismissedWarning")`, warning that unpaid classes get auto-cancelled the day before. Purely client-side state, no server round-trip; the dismissal is per-browser, not per-account.
- **`no-show-report-section.tsx`** — the no-show/refund-dispute widget shown on a completed class's detail page. Calls `createRefundRequest` and `escalateToAdmin` (`app/lib/actions/refund-requests.actions.ts`) via `useTransition`. Renders one of three states depending on whether a `RefundRequestData` already exists for the class: the submission form (no request yet), a status alert keyed off a `STATUS_CONFIG` map covering all six `RefundRequestStatus` values (`pending`, `accepted`, `refused`, `expired`, `admin_review`, `resolved`) with distinct label/color/icon per status, or an "Escalate to Admin" button (shown only when `status === "refused"`, mirroring the server-side rule that escalation is only valid from a refused request).
- **`open-requests.tsx`** — the broadcast/open-request claim panel shown to teachers, backed by `fetchOpenRequestsForTeacher`/`claimClass` (`classes.actions.ts`). Each row shows a **"Priority" badge** when `r.priority` is true, with a title tooltip explaining it's from a purchased Priority Booking perk — this is the UI-side confirmation that the `priority` flag is actively read and surfaced today (the query behind it orders priority-flagged requests first), not a vestigial field. `ClaimButton` wraps `claimClass` in `useTransition` and shows a spinner while pending; `claimClass` itself redirects on completion so there's no explicit success state to render here.
- **`paid-icon.tsx`** — a green check / red X for `Class.paid`, used inline in table rows.
- **`row-status-icon.tsx`** — a small icon (hourglass for pending, exclamation-circle for unpaid) rendered next to a row's subject/student name, *in addition to* the colored left-border the booked-classes tables already use. Its own comment explains why: a color-only signal (the border) isn't accessible to colorblind users, so this adds an icon + `title`/`aria-label` carrying the same information non-visually. If you touch the pending/unpaid visual language in these tables, keep both signals in sync.
- **`student-booked-classes.tsx`** / **`teacher-booked-classes.tsx`** — the two main "My Classes" table components (structurally near-identical, not factored into a shared component — see the `student-table-buttons.tsx`/`teacher-table-buttons.tsx` pair below for the same pattern). Both:
  - Take `BookedClass[]` (the shape produced by `fetchBookedClassesByUser`, which includes the `requestedBySelf` flag).
  - Implement client-side filter tabs (`all` / `pending` / `unpaid`), where `isPending` checks `status === "requested"` and **`isUnpaid` is literally `canPayForClass`** (`app/lib/classes/can-pay-for-class.ts`) aliased — reusing the exact same payability predicate the "Pay Now" button uses elsewhere, so the "Unpaid" filter tab and the button's own visibility can never disagree.
  - Row click navigates to the class detail page; the actions cell calls `e.stopPropagation()` so clicking an action button doesn't also trigger the row navigation.
  - Student version renders `totalPrice`/`teacher.name` (falling back to a "Finding…" badge when `teacher` is null — broadcast request still unclaimed); teacher version renders `student.name` and omits the "Finding…" case (a teacher's own booked classes always have a teacher, obviously).
- **`student-table-buttons.tsx`** / **`teacher-table-buttons.tsx`** — compute which actions are visally available for a row (`canAccept`/`canRefuse`/`canCancel`, plus `canPay` on the student side only) purely from `status` and `requestedBySelf`, then delegate rendering to the shared `details/class-action-modals.tsx` via a `role: "student" | "teacher"` prop. **Neither file talks to a server action directly** — they're pure derivation-plus-prop-passing, all actual mutation triggers live inside `class-action-modals.tsx`. This role-parameterized-shared-component pattern (one modal component branching on `role` rather than two forked components) recurs elsewhere in the app — e.g. `app/ui/main/regular-classes/regular-class-action-modals.tsx` is explicitly modeled after this same shape.

## `review/leave-review-form.tsx`

Folded into this README rather than given its own — it's a single, self-contained file. The review form shown on a completed class's detail page, calling `createReview` (`app/lib/actions/ratings.actions.ts`). Renders a 5-star `StarPicker` (hover-preview via local `hovered` state, label text like "Excellent"/"Poor" per star count) and a 500-char comment box. If `existingReview` is passed in (student already reviewed this class), it renders read-only from the start; after a successful submission it locally synthesizes a `Rating` object with placeholder `id: "new"`/`studentId: ""` to flip into the same read-only view without waiting for a re-fetch — so don't rely on those two fields being meaningful immediately after submit, only after the next real fetch.

## How it fits together

Everything here reads data already prepared by `app/lib/actions/classes.actions.ts` / `refund-requests.actions.ts` / `ratings.actions.ts` and calls their exported server actions directly from client components via `useTransition` (no separate API routes). The heaviest cross-file reliance is `canPayForClass` — reused identically by both booked-classes tables and (indirectly) by the pay button on the class detail page (`details/join-class-card.tsx` or the payment success flow), so the "is this payable" concept lives in exactly one place. `create/` (the container directory) has no files of its own — it's purely a namespace holding the `student/` and `teacher/` booking-form subdirectories.

## Gotchas

- `student-booked-classes.tsx` and `teacher-booked-classes.tsx` are near-duplicates by design (parallel to the create-form split, see `create/student` and `create/teacher` READMEs) rather than a shared generic table — if you fix a bug in one, check whether the same bug exists in the other.
- `row-status-icon.tsx`'s accessibility rationale (colorblind-safe redundant signal) is easy to accidentally regress if a future table redesign drops the icon and keeps only the border color.
- `open-requests.tsx`'s priority badge is a genuine signal now (see `classes.actions.ts`'s `fetchOpenRequestsForTeacher` ordering) — don't assume it's decorative-only leftover UI for an inert backend flag.
