# app/ui/main/classes/create/student

The student-side "book a class" flow, backing `app/main/student/classes/request/page.tsx`. Considerably more elaborate than its teacher-side counterpart (`create/teacher/`) because it has to cover three distinct booking paths in one wizard: on-demand broadcast, a specific teacher paid immediately after acceptance, and a specific teacher with payment pre-authorized up front.

## Key files

- **`create-class-form.tsx`** — the whole wizard, as a single large `"use client"` component (`RequestClassForm`), state-machine-style via a `phase: "details" | "teacher" | "payment"` local state (not URL-driven — refreshing mid-flow loses progress):
  1. **`"details"`** — subject, start time, duration. On submit, calls `fetchTeachersForBooking` (`app/lib/actions/teachers.actions.ts`) to get every teacher for that subject annotated with `isAvailable` (computed server-side via `isWithinAvailability`) and moves to phase 2.
  2. **`"teacher"`** — presents an "On-Demand" card (broadcast; the copy changes if `priorityBookingActive` is true, telling the student their request will be shown first) alongside individual `TeacherCard`s for every matching teacher, split into "Available at your time" vs. "Other teachers" sections. Note this component defines its **own inline `TeacherCard`**, not the shared `teacher-select.tsx` in this same directory (see Gotchas). Picking on-demand and continuing calls `createClassAsStudent` (`app/lib/classes/create-class-as-student.ts`) directly with a synthesized `FormData` — this is the plain broadcast-mode path, no payment step. Picking a specific teacher and continuing calls **`POST /api/payment-intent/pre-auth`** to create a Stripe pre-auth PaymentIntent, then moves to phase 3 — the specific-teacher path always pre-authorizes, it never falls through to `createClassAsStudent`'s own specific-teacher branch (that server function's specific-teacher mode exists but this form doesn't route through it — see Gotchas).
  3. **`"payment"`** — renders `PreAuthForm` (`app/ui/payment/pre-auth-form.tsx`, cross-reference the payments domain) with the intent's `clientSecret`, which on confirmation ultimately calls `createClassWithPreAuth`. An `onBack` prop lets the student return to phase 2 and abandon the pre-auth intent.
  - The estimated price preview in phase 2 applies a client-side-only 5% Study Boost discount display (`discountedPrice`) when `studyBoostActive` — this is purely a preview; the actual authoritative discount computation happens server-side in `createClassWithPreAuth` via `computeClassPrice`.
  - `minStartDate` mirrors the server-side "must be from tomorrow onward" rule as an HTML `min` attribute — client convenience only, `create-class-as-student.ts` re-validates it server-side regardless.
- **`subject-select.tsx`** — button-grid subject picker (not a `<select>` despite the name), writes to a hidden `name="subject"` input for the on-demand `FormData` path.
- **`start-time-input.tsx`** — a `datetime-local` input. Its `min` attribute is only applied when there's no `defaultValue`, with an inline comment explaining why: browsers silently clear a datetime-local field if `defaultValue` is earlier than `min`, so pre-filling a value (e.g. from a "book again" deep link) and enforcing the tomorrow-onward minimum are mutually exclusive on the same render.
- **`duration-select.tsx`** — a plain `<select>` of quarter-hour increments (0.25h–5h, `DURATIONS` array of length 20 defined in the parent), formatted as "45 min" / "1h" / "1h 30min" via a local `formatDuration` helper.
- **`teacher-select.tsx`** — a card-list teacher picker component. **Not used by `create-class-form.tsx` in this directory** (which has its own inline `TeacherCard`) — it's actually imported by `app/ui/main/regular-classes/request-regular-class-form.tsx` instead, since recurring-class requests always target a specific teacher and don't need the on-demand/available-vs-other split this form's inline version has. Kept in this directory because it's conceptually a "student classes create" component, not because it's used here.

## How it fits together / parallel with `create/teacher`

Both `create/student` and `create/teacher` have nearly identically-named files (`duration-select.tsx`, `start-time-input.tsx`, `subject-select.tsx`) that are **not shared** — each directory has its own copy, kept deliberately separate rather than factored into one shared component tree. The teacher-side versions are simpler (no `onChange` callback plumbing, since the teacher form doesn't need local state to drive a multi-phase wizard — it's a single-phase `useActionState` form). If you fix a bug in one copy (e.g. the datetime-local `min`/`defaultValue` interaction in `start-time-input.tsx`), check whether the same bug exists in the other directory's copy.

The student flow is the one that actually reaches the pre-auth/payment surface — the teacher flow (`create/teacher`) never touches Stripe at booking time, since a teacher-initiated request is paid by the student later via the normal "Pay Now" flow once accepted.

## Gotchas

- The specific-teacher path in this UI **always** goes through pre-auth (`/api/payment-intent/pre-auth` → `createClassWithPreAuth`), even though `createClassAsStudent`'s specific-teacher branch (immediate price computation, no pre-auth) still exists and is independently reachable/tested. Don't assume every call into `createClassAsStudent` comes from this form — broadcast mode is the only path this form actually drives into it.
- Phase state is local component state, not persisted to the URL or server — a page refresh mid-wizard loses all progress and restarts at phase 1.
- The Study Boost discount shown in phase 2 is a client-side preview computed from `estimatedPrice * 0.95`; it is not itself authoritative and must stay in sync with `computeClassPrice`'s actual discount math (`app/lib/classes/compute-class-price.ts`) if that ever changes.
