# app/ui/main/availability

The weekly-grid UI for setting and viewing teacher availability, backing `app/main/teacher/availability` (edit mode) and any student-facing teacher profile that shows a read-only schedule.

## Key files

- **`availability-grid.tsx`** — the core grid component (`AvailabilityGrid`), operated in one of two modes via a `readOnly` prop:
  - **Edit mode** (teacher managing their own schedule): click or **click-and-drag paints/erases** a range of 30-minute cells in one gesture. The drag state lives in refs (`isDraggingRef`, `dragValueRef`, `visitedRef`), not component state, mirroring the same "no stale closures in global listeners" pattern used by `weekly-schedule.tsx`'s calendar drag — a single global `mousemove`/`mouseup` pair (attached once) reads `document.elementFromPoint` and a `data-slotkey` attribute on the hovered cell to determine which slot is under the cursor, rather than requiring each of the ~300 individual cells to carry its own mouse handlers. `dragValueRef` is set once at drag-start based on whether the initial cell was active (dragging from an active cell erases; from an inactive cell paints on) — so a single drag gesture is either all-paint or all-erase, never mixed. Four **quick-add presets** (weekday mornings/afternoons/evenings, weekends) union additional slots into the active set in one click rather than requiring manual painting. Saving computes `endHour`/`endMin` per slot (`+30min` or roll to the next hour) and calls `setAvailability` (`app/lib/actions/availability.actions.ts`), which does the actual delete-then-recreate.
  - **Timezone selector** (edit mode only, added 2026-08-05 alongside #128's fix): a `<select>` populated via `Intl.supportedValuesOf("timeZone")` (all IANA zones, with a small fixed fallback list if that API is somehow unavailable), defaulting to `initialTimezone` (the teacher's currently-saved `User.timezone`). This is what tells the server what the grid's hour labels actually *mean* — the grid itself still just paints day/hour/minute integers, it has no timezone awareness of its own; `handleSave` passes the selected timezone alongside the slots to `setAvailability`, which persists it to `User.timezone` in the same transaction. `hasUnsaved` accounts for a bare timezone change (no slot edits) too, not just slot-set changes.
  - **Read-only mode** (student viewing a teacher's schedule, or a teacher's own bookings overlaid): cells are colored green ("available — click to book"), red ("already booked", from a separate `bookedSlots` prop layered on top of `initialSlots`), or neutral. Clicking a green (free) cell fires `onSlotClick(day, hour, min)` rather than mutating anything locally — this component has no fetch/mutate logic of its own in read-only mode, it's purely a controlled display + click-relay.
  - **Mobile scroll hint**: same `sm:hidden` "Scroll sideways…" pattern as `weekly-schedule.tsx`'s calendar — the grid's `min-w-[420px]` inner wrapper forces horizontal scroll on narrow viewports.
  - `hasUnsaved` is computed by comparing sorted, joined slot-key sets between `active` and the original `initialSlots` — a full-set string comparison rather than a diff, simple but means a 300-slot grid does a moderately large string join on every render where `active` changes; not currently a perceptible cost given the actual grid size (7 days × 30 slots).
- **`teacher-availability-view.tsx`** — a thin wrapper (`TeacherAvailabilityView`) around `AvailabilityGrid` in its read-only mode, used on a teacher's public profile. Accepts an optional `timezone` prop (the teacher's `User.timezone`) purely for display — renders a small "(times shown in Europe/Lisbon)"-style label next to the section heading so a student isn't left guessing what timezone the grid's hour labels are in. `handleSlotClick` computes the *next upcoming occurrence* of the clicked weekday/time and navigates to `/main/student/classes/request?teacher=...&startTime=...` — pre-filling the booking form exactly like the calendar's drag-to-schedule flow does. **Known gap** (deliberately not fixed alongside #128, see the inline comment in this file): the pre-fill math uses the *browser's* local time (`setHours`/`getDay`) to interpret the clicked day/hour/minute, not the teacher's timezone — so a student in a different zone than the teacher can get a slightly-wrong suggested time in the booking form. Not a security/correctness issue since the actual booking is re-validated server-side against `isWithinAvailability` with the teacher's real timezone; just a UX rough edge left for a follow-up. Renders nothing (`return null`) if the teacher has zero availability slots — consistent with `isWithinAvailability`'s "no slots = always available" rule elsewhere, this component doesn't try to represent that state visually, it just omits the whole card.

## How it fits together

`AvailabilityGrid`'s edit-mode save path is the only place in the UI that calls `setAvailability`, which is the only writer of both `TeacherAvailability` rows and (as of #128) `User.timezone` — the single source of truth those rows feed is `isWithinAvailability` (`app/lib/availability/check-availability.ts`), used at booking time across **four** separate call sites (see that directory's README — this was previously miscounted as three). The grid's own slot-key format (`"day-hour-min"`) is a UI-local convention, translated to/from the `AvailabilitySlot`/`{dayOfWeek, startHour, startMin}` shape at the read (`initialSlots`) and write (`handleSave`) boundaries — it has no relationship to how slots are stored in the database beyond that translation. Critically, **the day/hour/minute integers themselves are meaningless without the teacher's timezone** — `isWithinAvailability` now requires it (defaulting to `"UTC"` only for backward-compatible callers that don't pass one) to correctly convert a booking's UTC instant into the teacher's local calendar terms before comparing against the stored slots.

## Gotchas

- The grid's day convention (`DAY_VALUES = [1,2,3,4,5,6,0]`, i.e. Mon-first for display but using JS's `0=Sun` numbering underneath) is easy to get backwards if you're adding a new day-of-week-aware feature — `DAYS` is the display order, `DAY_VALUES[i]` is the actual `dayOfWeek` value stored/queried.
- `bookedSlots` (read-only mode) and `active`/`initialSlots` (availability) are two independent inputs that can overlap or not — a cell can be simultaneously "in the teacher's stated availability" and "already booked," which is exactly the red-vs-green distinction read-only mode renders; don't conflate the two sets.
- The timezone `<select>` only exists in edit mode — the read-only view shows the teacher's timezone as inert text (see `teacher-availability-view.tsx` above), it can't be changed from a student-facing page.
