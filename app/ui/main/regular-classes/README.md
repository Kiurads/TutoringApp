# app/ui/main/regular-classes

The UI for the `RegularClass` (recurring series) domain: requesting a weekly slot, the teacher's accept/refuse/cancel actions, and the listing table — all thin wrappers around `app/lib/actions/regular-classes.actions.ts`.

## Key files

- **`day-of-week-select.tsx`** — a button-grid day picker (Sun–Sat), structurally identical to `create/student/subject-select.tsx`'s button-grid pattern (hidden `name="dayOfWeek"` input, active/inactive button styling) — a separate, small, self-contained component rather than a shared generic "pill picker."
- **`regular-class-action-modals.tsx`** — accept/refuse/cancel confirmation modals for a single `RegularClass`, explicitly modeled after `app/ui/main/classes/details/class-action-modals.tsx`'s shape: real `<dialog>` elements driven by `showModal()`/`close()` (its own inline comment cross-references that file for the focus-trap/Escape-to-close rationale), a `ModalType | null` `open` state, `useTransition`-wrapped server-action calls. Simpler than its one-off counterpart because a `RegularClass` has no pay/counter-offer actions — those concepts don't apply at the series level (payment is per-occurrence via the existing immediate-capture flow, and there's no per-occurrence negotiation once a series is active). The cancel confirmation copy explicitly warns "Future sessions will be cancelled — each following its own refund policy if already paid. Past sessions are not affected," matching `cancelRegularClass`'s actual behavior (loops `cancelClassCore` over future non-terminal occurrences only).
- **`regular-classes-table.tsx`** — lists a user's `RegularClass` rows (`role`-parameterized to show the counterpart's name: teacher's name for a student viewer, student's name for a teacher viewer), with a `StatusBadge` mapping `active`→success, `requested`→warning, else ghost (covers `inactive` — no distinct color, same neutral badge as any other terminal/unlisted status). Computes the row's available actions inline rather than delegating to a `requestedBySelf`-style prop the way the one-off classes tables do: `canAccept`/`canRefuse` are teacher-and-`requested`-only (a `RegularClass` is always requested by the student, so there's no teacher-initiated recurring request to symmetrically handle — unlike one-off classes, `create-class-as-teacher.ts` has no recurring-series counterpart), `canCancel` covers both `requested` and `active`.
- **`request-regular-class-form.tsx`** — the student's request form, reusing several `create/student` field components directly (`SubjectSelect`, `TeacherSelect` — the *card-list* teacher picker, not `create-class-form.tsx`'s inline one, see `create/student`'s README — and `DurationSelect`), plus its own `DayOfWeekSelect` and a plain `<input type="time">` (no custom time-picker component). The interesting part is the **payment-method gate built into the submit flow**:
  - On mount, checks `getPaymentMethodStatus()` (`payment-methods.actions.ts`). If the student already has a saved default payment method, the form's `action={formAction}` submits normally straight to `requestRegularClass`.
  - If not, submitting instead intercepts (`e.preventDefault()`), calls `POST /api/setup-intent` to get a Stripe SetupIntent `clientSecret`, and swaps to a "payment" phase rendering `SetupCardForm`. Once the card is saved (`handleCardSaved` → `saveDefaultPaymentMethod`), it calls `formEl?.requestSubmit()` on a `<form>` ref captured earlier — **programmatically re-submitting the same underlying form-action form** now that a payment method exists, rather than duplicating the request logic. This is why the form keeps a raw `HTMLFormElement` ref (`formEl`) even though it's otherwise a fairly standard `useActionState` form.
  - This gate exists because recurring occurrences are charged off-session automatically (`materializeOccurrences`, see `app/lib/regular-classes/README.md`) — there's no per-occurrence "Pay Now" moment the way one-off classes have, so a payment method has to be on file *before* the series can be requested at all.

## How it fits together

Every mutating action here funnels through `regular-classes.actions.ts`. The request form additionally touches the Stripe SetupIntent API route and `payment-methods.actions.ts` for the card-on-file gate described above — this is the one place in the recurring-class UI that talks to Stripe directly, everything else (occurrence charging) happens invisibly in the background via `materializeOccurrences`.

## Gotchas

- `regular-class-action-modals.tsx`'s parallel structure to `class-action-modals.tsx` means a UX fix made to one (e.g. dialog accessibility behavior) should be checked against the other.
- `request-regular-class-form.tsx`'s `formEl?.requestSubmit()` re-submission trick is easy to break if the form's `action`/`onSubmit` wiring is refactored — the re-submit relies on the same `<form>` element still being mounted with the same `action` bound when the payment phase resolves.
- `regular-classes-table.tsx`'s status badge treats `inactive` (a refused-or-cancelled series) with the same neutral ghost badge as any unrecognized status — there's no visual distinction in this table between "never accepted" (refused) and "cancelled after being active," though the state transitions themselves are different in `regular-classes.actions.ts`.
