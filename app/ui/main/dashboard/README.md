# app/ui/main/dashboard

Widget components rendered on the student/teacher dashboard home pages. **Mixed-domain directory** — gamification widgets, a class-lifecycle "what's next" card, payment-summary widgets, and a generic header all live here side by side because they're assembled onto the same dashboard grid, not because they share ownership. Each widget is an independent async Server Component (except the two `"use client"` button/list pieces) that does its own data fetching; there's no shared dashboard-level data-loading layer.

## Files

### Gamification widgets

- **`academic-arc-widget.tsx`** — Student-side rewards summary card. Fetches `StudentGameProfile` directly via Prisma (`findUnique`), derives tier name/progress via `getTierName`/`getTierProgress` (`@/app/lib/gamification-utils`), and shows: gem balance, weekly activity streak (`currentStreakWeeks`, only rendered when `>0`, plus a snowflake badge for banked `streakFreezes`), a tier progress bar (hidden once `tier >= 4`, i.e. max tier "Sage"), and the 3 most recently earned badges (`UserBadge.earnedAt desc`, `take: 3`) rendered inline — this is a separate, simpler inline rendering from `BadgeShowcase` in `app/ui/main/badges/`, not a reuse of it.
- **`mentor-milestones-widget.tsx`** — Teacher-side mirror of `academic-arc-widget.tsx`: same shape, but reads `TeacherGameProfile` (`reputationSparks`, `mentorshipRank` via `getRankName`/`getRankProgress`), labels its badge strip "Expertise seals" instead of "Recent badges," and uses `badge-accent`/`progress-accent` styling instead of `badge-primary`/`progress-primary` to visually distinguish the teacher track from the student track.
- **`weekly-quests-widget.tsx`** — Renders the current week's quests from `fetchWeeklyQuests()` (`@/app/lib/quests`) — role-aware (student sees `weekly_2_classes`/`weekly_leave_review`, teacher sees `weekly_3_classes`), returns `null` entirely if there are no quests for the signed-in role (e.g. admin). Each quest shows a progress bar and delegates the claim action to `ClaimQuestButton`. Progress here is *not* stored — `fetchWeeklyQuests` computes it live from `Class`/`TeacherRating` rows scoped to the current UTC week (`getWeekStart`); only the *claim* is persisted (`QuestClaim`, for idempotency).
- **`claim-quest-button.tsx`** (`"use client"`) — Three-state button: shows a static "+N" hint if the quest isn't complete yet, a "Claim +N" button once `completed` is true, or a "Claimed" badge once claimed. Calls `claimWeeklyQuest(questKey)` (also in `@/app/lib/quests`), which re-derives progress server-side before paying out (never trusts the client's `completed` flag) and awards gems (student) or sparks (teacher) via `awardGems`/`awardSparks`.

### Other domains (described here for completeness, not owned by gamification)

- **`header.tsx`** — Generic dashboard header card: greeting, role badge, avatar (with frame overlay via `getFrameClass` — the one place in this directory outside the two rewards widgets that touches the gamification system, since frames are gamification-earned but shown as a generic profile decoration here), member-since date, and total class count (`fetchClassesByUser`). Not otherwise specific to any one domain.
- **`next-up-card.tsx`** — Class-lifecycle widget ("what's coming up"): finds the single next `scheduled` class (`startTime > now`, ordered ascending) for the signed-in user as either student or teacher, and shows subject/counterparty/relative time-until plus a "View details" link. Belongs to class-lifecycle, not gamification.
- **`student-payments.tsx`** — Payment-history summary table for students: total spent + a table of individual payments with a per-row "View" receipt link. Pure presentational component, takes a `Payment[]` prop (plain `number` amounts, already normalized by the caller) — belongs to the payments domain.
- **`teacher-earnings.tsx`** — Payment-history summary table for teachers: total earned + this-month earned, then a table of payments. Unlike `student-payments.tsx`, this one takes `amount: Decimal` (Prisma's `Decimal` type from `@prisma/client/runtime/library`) and calls `.toNumber()` itself — a reminder that these two "twin" widgets aren't actually sharing a type or a normalization step, so don't assume payment-shaped props are interchangeable between them.

### `upcoming-classes/` subdirectory

- **`upcoming-classes/upcoming-classes.tsx`** — The only file in this subdirectory (folded into this README rather than getting its own, per the flat structure elsewhere). Fetches `fetchUpcomingClassesByUser(userEmail)` and renders a table (subject, teacher, date/time, duration via `decimalStringToHours`, price, status via `ClassStatusBadge` imported from `../../classes/class-status-badge`). This is a full upcoming-*classes* table (plural, ongoing schedule), distinct from `next-up-card.tsx`'s single-next-class summary card — both can appear on the same dashboard without redundancy since they answer different questions ("what's my whole week look like" vs. "what's immediately next").

## How it fits together

None of these widgets import each other — they're independently composed by whatever dashboard page assembles the grid (student dashboard vs. teacher dashboard use different subsets). The two gamification widgets (`academic-arc-widget.tsx`, `mentor-milestones-widget.tsx`) and `weekly-quests-widget.tsx` all read live from Prisma/`gamification-utils`/`quests.ts` on every render — none of them cache or receive gamification state as props, unlike `student-payments.tsx`/`teacher-earnings.tsx` which are pure presentational components fed by the page.

## Gotchas

- `academic-arc-widget.tsx` and `mentor-milestones-widget.tsx` both silently `return null` if `fetchUserByEmail` can't resolve the session email — no error state, no loading skeleton, just an absent card.
- The weekly streak displayed here (`currentStreakWeeks`/`longestStreakWeeks`/`streakFreezes`/`lastActivityAt`) is a genuinely live, actively-updated mechanic — see the extensive design-rationale comments in `app/lib/gamification.ts`'s `updateActivityStreak` (weekly not daily cadence, freeze-based grace period, deliberately no loss-aversion notification when a streak breaks). It's driven from class completion (both the worker's `markCompletedClasses` and the manual `completeClass` action call `updateActivityStreak`), not from any code in this directory.
- `header.tsx` computes `frameClass` conditionally on `user.role === "student"` — teacher accounts never render a frame overlay even though `TeacherGameProfile` has no `activeFrame` field to render anyway (frames are a student-only cosmetic), so this isn't a bug, just worth knowing if you're tracing why a teacher's avatar never shows a frame.
- `teacher-earnings.tsx`'s "this month" calculation compares `getMonth()`/`getFullYear()` using the server's local timezone (via `new Date()`), not UTC — inconsistent with the UTC-anchored week boundary (`getWeekStart`) used elsewhere in the gamification/quests code. Flagged as a latent inconsistency, not fixed here.
